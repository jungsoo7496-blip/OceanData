## 0. 결론

### 0.1 수렴 판정
세 문서는 **방향·원칙·구조에서 사실상 일치**한다. 남은 차이는 판단이 아니라 표기(필드명·코드·ID)의 불일치, 몇 개의 사실 오류, 그리고 네 개의 소소한 우선순위 차이였다. v0.04에서 모두 정리했다(2장).

**더 이상의 AI 간 교차 검토는 효과가 작다.** 다음 개선은 실제 입력값에서 나온다: 기업별 데이터 연계 카드, 기존 장비 실사, 보고 양식, 법률 자문, 스토리지 견적. 이 값이 들어오면 v0.1(실측 반영판)로 넘어간다.

### 0.2 핵심 결론 12가지
1. **만드는 것은 "실증업무 워크스페이스 + 자동수집 + 표준화 + 승인형 공동활용"이다.** 기업은 실증일지·보고서·영상검색 때문에 쓰고, 데이터는 그 과정에서 쌓인다.
2. **업로드 ≠ 공유.** 기본값은 L0(기업 단독). 관리기관 제출(L1)과 공동활용(L2~L4)은 별도 승인·별도 공간이다.
3. **공유 요청은 부산물(환경) 데이터로 한정한다.** 핵심 데이터(성능·알고리즘·튜닝값)는 시스템이 공유 자체를 막는다.
4. **중앙으로 무엇을 가져올지(C0~C3)를 기업·장비별로 정한다.** 이 한 가지가 스토리지 규모·법적 위험·회선 부담을 동시에 결정한다.
5. **2026년 남은 두 달은 개발이 아니라 조사·표준·계약이다.** G0(11월) 연계 카드, G1(12월) 표준·API·약정 동결.
6. **NGSI-LD는 조건부.** 도입 게이트 5개를 모두 충족할 때만 어댑터로 붙인다.
7. **API 게이트웨이·통합 인증은 필수, 마켓플레이스는 승인형 카탈로그로 축소, 크롤러는 제외하고 공공 Open API 수집으로 대체.**
8. **GPU는 선별 처리용이다.** 샘플링 태깅 + 공유 후보만 비식별하면 1~2천만 원급 1대로 연간 약 70일 분량.
9. **PB 구매는 판단 규칙(13.5)으로 결정한다.** 단, 장비 100대 규모가 되면 선별 수집이어도 2년 내 PB급에 도달한다(13.3 정정).
10. **원본 전체를 백업하지 않는다.** 원본은 장애보호 + 기업 현장 사본, 독립 백업은 메타·증빙·비식별본·데이터셋.
11. **MinIO 커뮤니티판은 쓰지 않는다.** 2026년 2월 저장소가 아카이브되어 유지보수가 끝났다.
12. **성과는 저장량이 아니라 자동수집 연결률·보고 시간 절감·승인 데이터 실제 활용 건수로 본다.**

## 1. 사업 개요

### 1.1 사업 여건 (공식 문서로 재확인 필요)
- 참여 특구기업 선정 완료, 2027년 실증 예정(정확한 개시 월 미정)
- 총사업비 약 20억 원 (부가세·운영비·유지보수 포함 여부 미확인)
- 기존 서버 보유, 스토리지 신규 구매, GPU는 1~2천만 원급 워크스테이션

### 1.2 목표
1. 실증기업이 추가 수작업 없이 데이터를 안전하게 수집·축적
2. 해양 영상·센서·운항·실증성과 데이터를 일관된 메타데이터와 품질 규칙으로 관리
3. 기업에 실질적으로 유용한 실증업무 서비스 제공
4. 기업 권리를 보존하면서 승인형 공동활용 구현
5. 특구 종료 후에도 남는 데이터셋·표준·API·운영절차

### 1.3 비목표
- 모든 장비와 즉시 연결되는 범용 CCTV/NVR 커넥터
- 모든 영상의 24시간 중앙 업로드, 무제한 무료 보관
- AI 탐지 결과를 사람 검증 없이 공식 실증 성능으로 확정
- 블러 처리만으로 외부 자유 배포 허용
- 데이터 거래·결제·정산·크레딧
- 이용기업 대상 대규모 AI 학습용 GPU 제공
- 웹 크롤링

### 1.4 설계 원칙
- 업로드는 업무의 부산물이어야 한다
- 업로드와 공유는 분리, 기본값은 L0
- **외부 이용기업에는 원본을 제공하지 않는다** (중앙 보관 자체는 계약·적법성에 따라 허용)
- 영상 파일이 본체, 표준 API는 창구
- 모든 데이터는 `기관 → 실증사업 → 실증회차 → 장비 → 자산` 구조로 들어온다
- 가진 자원에 맞춰 처리한다 (샘플링·선별)
- 모든 접근과 변경은 기록된다 (감사 로그 + 무결성 해시)
- 표준·API·데이터 권한 규격은 공급사가 아니라 발주기관이 소유한다
- 확실하지 않은 값은 지어내지 않는다 (촬영시각 미상은 "미상"으로 기록)

### 1.5 이해관계자

| 주체 | 역할 | 원하는 것 |
|---|---|---|
| 운영기관(컨소시엄) | 구축·운영·큐레이션 | 데이터 축적, 공급 실적, 운영 지속성 |

### 2.5 v0.04에서 새로 추가한 판단
- **data_role(핵심/부산물)을 필드로 만들고, 공유 가능 조건을 시스템이 강제하는 규칙표(3.3)** — 그동안 "원칙"이었던 것을 검사 가능한 규칙으로 바꿈
- **처리위탁 계약의 한계**: 위탁받은 플랫폼은 위탁 목적(보관·검색·가공 대행) 안에서만 처리할 수 있으므로, 공동활용·자체 데이터셋 구축은 별도 계약·근거가 필요 → 약정서를 2단 구조로 설계 (14.1)
- **100대 규모 경고**: 선별 수집이라도 전량 프록시를 장기 보관하면 PB급에 도달 → 프록시 보존 기간을 정책 변수로 명시

## 3. 용어·코드 사전 (기준선)

### 3.1 계층 용어

| 용어 | 코드 필드 | 정의 |
|---|---|---|
| 기관 | organization_id | 데이터 제공 법적 주체 |
| 실증사업 | project_id | 특구 실증과제 |
| 실증회차 | session_id | 한 번의 실증 수행 단위 (예: 2027-05-10 야간 운항) |
| 장비 | source_system_id | 카메라·NVR·센서·수집기 |
| 자산 | asset_id | 파일·객체 1건 |
| 업로드 세션 | upload_id | 한 번의 전송 작업 (API용) |
| 데이터셋 | dataset_id + version | 공동활용용 묶음 (수정 불가 버전) |

### 3.2 다섯 개의 독립 속성
하나의 "공개 등급" 필드로 합치지 않는다. 합치면 사고가 난다.

| 속성 | 질문 | 값 | 기본값 |
|---|---|---|---|
| **collection_mode** | 중앙으로 무엇을 가져오나 | C0_METADATA_ONLY / C1_SAMPLE_PREVIEW / C2_EVENT_CLIPS / C3_APPROVED_FULL | 연계 카드로 기업·장비별 지정 |
| **data_role** | 기업 경쟁력과 관련 있나 | CORE (성능·알고리즘·튜닝·실패사례) / BYPRODUCT (환경·배경 영상) | CORE (안전한 쪽) |
| **privacy_status** | 개인정보 처리 상태는 | UNKNOWN / NOT_APPLICABLE / REVIEW_REQUIRED / PSEUDONYMIZED / ANONYMIZED_VERIFIED | REVIEW_REQUIRED |
| **sensitivity_class** | 보안 민감도는 | INTERNAL / RESTRICTED / SECURITY (민감 해역·시설) | RESTRICTED |
| **sharing_scope** | 누가 볼 수 있나 | 아래 L0~L4 | L0 |

| 표시 | sharing_scope 코드 | 접근 범위 |
|---|---|---|
| L0 | PRIVATE | 제공기업만 |
| L1 | PROGRAM_REVIEW | + 관리기관 (협약상 제출 지표·증빙만, 원본 비노출) |
| L2 | SANDBOX_PARTNERS | + 특구 참여기업 |
| L3 | APPROVED_PARTNERS | + 심사된 외부 이용기업 |
| L4 | PUBLIC | 누구나, 광역 허브 연계 대상 |

### 3.3 공유 가능 조건 (시스템 강제 규칙)

| 목표 등급 | 시스템이 검사하는 조건 (모두 충족) |
|---|---|
| L1 | 기업 관리자의 제출 승인 |
| L2 | data_role = BYPRODUCT · privacy_status ∈ {NOT_APPLICABLE, PSEUDONYMIZED, ANONYMIZED_VERIFIED} · 검수 완료(REVIEWED) · sensitivity_class ≠ SECURITY · legal_basis_ref 존재 · 기업 관리자 승인 |
| L3 | L2 조건 + 데이터셋 버전으로 패키징 + 운영기관 승인 + 이용자 약정 |
| L4 | data_role = BYPRODUCT · privacy_status ∈ {NOT_APPLICABLE, ANONYMIZED_VERIFIED} · sensitivity_class = INTERNAL · 기업·운영기관 공개 승인 |
| 공통 | data_role = CORE는 L1까지만. 등급 상향은 감사 로그에 사유와 함께 기록 |

### 3.4 처리 상태와 공유 상태는 별도 필드

**ingest_status (수집·처리)**
```text
DISCOVERED → UPLOADING → RECEIVED → VALIDATING
  ├ QUARANTINED / REJECTED (사유·수정 요청)
  └ REGISTERED → PROXIED → READY_PRIVATE
```

**share_status (공유)**
```text
NONE → CANDIDATE (기업 지정, data_role=BYPRODUCT만)
  → LEGAL_REVIEW → PROCESSING (비식별) → QUALITY_REVIEW
  ├ REJECTED / REPROCESS
  └ APPROVED (L2 또는 L3) → (이용 신청별) GRANTED → EXPIRED / REVOKED
```
RECEIVED는 품질 합격이 아니고, 블러 처리 완료는 외부 제공 가능을 뜻하지 않는다.

### 5.2 기업 유형별 사용 흐름
- **선박**: 선내 폴더·수집기 연결 → 항해 중 로컬 저장 → 접안 시 자동 전송 → 시간·선박·항차·장비 연결 → 야간·부유물 검색 → 증빙 연결 → 보고서 초안
- **해수욕장 CCTV**: NVR/VMS 연계 가능성 확인 → 엣지가 이벤트·샘플만 선별 → (필요 시) 현장 비식별 → 이벤트 검토·오탐/미탐 근거 → 안전 실증 자료
- **센서·IoT**: API/MQTT/CSV 자동 전송 → 단위·시간대·교정정보 매핑 → 누락·이상치 검증 → 조건별 표 → 보고서
- **AI 실증**: 모델 버전·시험회차 등록 → 추론 결과와 원본 연결 → 정답·산출식 등록 → 재계산 가능한 지표. AI 추정값을 사람 검증 없이 공식 성능으로 확정하지 않음

### 5.3 화면 3종
- **실증기업 워크스페이스**: 내 실증 / 내 데이터 / 내 증빙 / 보고·분석 / 공유·권한 / 지원
- **관리기관 보드**: 기업별 진행·수집 정상성·제출 지표·증빙 검토 (원본 비노출, 원본 열람 관제실이 아님)
- **이용기업 카탈로그**: 승인 데이터셋·데이터 카드·신청·제공

### 5.4 보고 자동화의 전제
- 실제 제출 양식 먼저 확보(G1)
- 자동 집계 지표(촬영시간·가동률·수집량)와 사람이 검증할 지표(정량 성능·안전성 판단) 구분

- 출력: PDF·Excel·HWP/HWPX

## 6. 공공 표준 모듈 판단

"데이터 코어(NGSI-LD) / API 게이트웨이 / 통합 보안 / 데이터 수집 / 마켓플레이스 / 광역 허브 연계"는 국내 스마트시티 데이터 허브의 구성이다. 이 허브는 구조화된 상태 데이터 중심이고 본 플랫폼의 본체는 대용량 영상이다. RFP에 모듈명은 유지하되 내용은 아래로 정의한다. 모듈명은 논리 기능이며 솔루션 개수·라이선스 수량이 아니다.

### 6.2 판단표

|---|---|---|---|
| 데이터 코어(NGSI-LD) | **조건부** | 게이트 통과 시 장비·선박·상황 엔터티 어댑터. 영상은 asset_id 참조만. RFP에 "데이터 코어"가 필요하면 "공통 메타데이터 + 상태·품질 + API" 논리 기능으로 정의하고 NGSI-LD 범위는 별도 명시 | STD, DB, INT-01 |

| DB 아키텍처 | **필수** | 11.4 | DB |

### 6.3 NGSI-LD 도입 게이트 (모두 충족 시)
1. 외부 규격 요구서(사업계획·협약·연계 대상 문서)
2. 대표 사용 사례 2개 이상

4. 유지보수 가능한 브로커와 운영 인력
5. 실제 표준 적합성 시험 계획 (엔드포인트 이름이나 JSON-LD 형식만 흉내 낸 것은 "지원"이 아님)

### 7.1 3단계 구조
1. 공통 메타데이터 코어 (모든 유형)
2. 유형별 확장 프로파일 (영상·CCTV·선박·센서·외부관측·어노테이션·실증 성능)
3. 데이터셋 패키지 (파일 목록·스키마/데이터/가공 버전·데이터 카드·이용조건·체크섬·배포 이력)

기업의 원시 포맷을 바꾸라고 요구하지 않는다. 들어오는 모든 데이터에 같은 식별 체계와 메타데이터를 붙인다.

### 7.2 공통 규칙
- **시간**: UTC, ISO 8601/RFC 3339로 저장, 화면은 KST. **파일 생성시각을 촬영시각에 대입하지 않는다.** 근거가 없으면 capture_start_at을 비우고 timestamp_quality = UNKNOWN + 품질 경고
- **위치**: WGS 84(EPSG:4326), GeoJSON 좌표 순서 `[경도, 위도]`. 원천 좌표계·변환 이력 기록. 민감 위치는 location_precision으로 공개 정밀도 제한
- **단위**: SI 기반 단위 사전 (°C, m, knot↔m/s 변환 규칙). 원래 측정값 보존
- **코드표**: 기관·사업·회차·장비·이벤트·관측항목·품질·권한·보존 정책. 이벤트는 공통 상위분류(선박·사람·부유물·기상/파랑·장비 장애·안전사고) + 기업별 하위코드
- **ID 계보**: 기관 → 사업 → 회차 → 장비 → 자산 → 이벤트 → 가공 자산 → 데이터셋 버전 → 배포
- **멱등성**: 파일명이 아니라 `기관 + 장비 + 해시 + 에이전트 수집 ID`로 중복 판단
- **스키마 버전**: 주·부 버전, 필수 필드 삭제·의미 변경은 주버전, 하위호환 기간과 폐기 예정일 공지

## 8. 수집·연계

### 8.1 수집 경로

| 경로 | 대상 | 우선 | 핵심 |
|---|---|---|---|
| 폴더 동기화 에이전트 | 연구 PC, NAS, 선내 PC | P0 | 감시·증분·재개·멱등·시간대 제한·하트비트 |
| 웹 대용량 업로드 | 개발 여력 없는 기업, 문서 | P0 | 분할·재개·실패 원인 |
| REST + S3 업로드 | 자체 서버 보유 기업 | P0 | 단기 업로드 권한·멀티파트·완료 신고·SDK |
| 선박 엣지(store-and-forward) | 해상 단절 | 앵커 P0 PoC, 확대 P1 | 로컬 버퍼·접안 전송·대기량 알림 |
| CCTV 엣지(push)·NVR/VMS 커넥터 | 해수욕장·항만 | 앵커 P0 PoC, 확대 P1 | 바깥으로만 연결, 현장에서 클립·프록시 |
| 센서 IoT 어댑터 | MQTT/REST/CSV | 대상 기업 P0 | 시간·단위·순서·지연 |
| 공공 Open API 수집기 | 기상·해양 관측 | P0(소스 1~2개) | 갱신 주기·이용조건·스키마 변경 감시 |

### 8.2 collection_mode별 운영

| 코드 | 중앙으로 오는 것 | 적합 사례 | 용량 |
|---|---|---|---|
| C0_METADATA_ONLY | 존재·장비·시간·권한 메타데이터만 | 원본 이전 불가 CCTV, 민감 원본 | 최소 |
| C1_SAMPLE_PREVIEW | + 샘플 프레임·프록시 | 긴 영상 검색, 기술 검증 | 낮음 |
| C2_EVENT_CLIPS | + 이벤트 전후 클립 | 해수욕장 이벤트, 해상 장애물 | 중간 |
| C3_APPROVED_FULL | 계약·법적 근거·회선·용량 심사를 통과한 원본 | 보존 의무, 특정 검증 | 매우 큼 |

collection_mode는 공개 등급이 아니다. C3로 들어온 원본도 기본은 L0다.

### 8.3 에이전트 요건
- 최초 1회 기관·사업·장비·폴더 등록 후 자동 실행
- 쓰기 완료 확인 후 전송, 변경·삭제 이벤트 처리 규칙
- SHA-256, 서버 재검증, 업로드 영수증
- 파트별 재시도·재개, 멱등성 (7.2 규칙)
- 시간대·대역폭 제한, 접안 스케줄, 로컬 저장 임계치 경고
- 하트비트(마지막 정상 수집·대기량·버전)
- 수집 전 정책 점검 (유형·회차·collection_mode·data_role 기본값)
- **로컬 원본은 자동 삭제하지 않는다** (13.7 계층형 백업의 전제)
- 서명된 자동 업데이트·롤백, 자동 업데이트 금지 기업은 수동 절차
- 권한 회수 시 즉시 차단, 캐시·키 처리 규칙
- 사내망 제약 대응 (프록시 설정, 설치형/비설치형)

### 8.4 대용량 전송 원칙
- 제어(인증·세션·메타)는 게이트웨이, 바이너리는 단기 권한으로 스토리지 직송
- 장기 관리자 키를 현장에 배포하지 않는다
- S3 호환 제품마다 멀티파트·수명주기 동작이 다르므로 실측
- 선박 접안 시간 안에 며칠 분량이 올라가는지 회선·우선순위·현장 디스크를 먼저 검증
- 초기 대량 원본은 암호화 디스크 반입을 보조 경로로

### 8.5 CCTV 현장 비식별 옵션

| | 센터 비식별(기본) | 현장 비식별(옵션) |
|---|---|---|
| 장점 | 장비 단순, 품질 관리·재처리 쉬움 | 개인정보 포함 원본이 현장을 떠나지 않음 |
| 단점 | 원본 이전의 법적 근거 필요 | 현장마다 추론 장비, 모델 갱신·품질 관리 어려움 |
| 적용 | 원본 이전 근거 확보 기업 | 원본 이전이 어려운 기업 (Q08) |

### 8.6 수집 거부·격리
- 체크섬 불일치 → 재전송
- 필수 메타 누락·회차 미상 → 격리 + 기업 알림
- 손상·미지원 → 격리 (30일 후 삭제)
- 단위·시간·좌표 오류 → 규칙별 경고 또는 거절
- 검증 실패 데이터는 삭제하지 않고 사유 이력과 함께 격리

## 9. API 규격 (기준선)

### 9.1 원칙
- 내부 도메인 API는 하나, 기업 전송 경로는 다양하게
- OpenAPI 3.x·JSON Schema·오류 코드·예제·샌드박스·계약 테스트
- 사용자·서비스·현장 기기 자격 분리, 권한은 기관·사업·회차·데이터셋·목적·기간으로 검사
- **수신 성공과 품질 검증 통과를 구분해 응답**
- Idempotency-Key 또는 upload_id로 중복 방지
- 비동기 작업 상태 조회·웹훅(서명 검증)
- v1 하위호환, 변경 사전 공지
- 업로드 자격과 포털 로그인 세션을 같은 영구 키로 묶지 않는다
- "인가됨"과 "이용 권리 있음"은 다르다

### 9.3 업로드 시퀀스
```text
① 기기 인증 + 장비 정책 조회 (collection_mode·쿼터·시간대)
② 매니페스트 생성 (기관·회차·장비·촬영시각·해시·크기·data_role)
③ POST /v1/uploads → 정책·쿼터 검사 → 단기 업로드 권한
④ 스토리지 수신 구역으로 멀티파트 직송 (중단·재개)
⑤ POST /v1/uploads/{id}/complete
⑥ 크기·해시·형식·악성코드(대상 시)·스키마 검증
⑦ L0 자산 등록 + 영수증 (ingest_status = REGISTERED)
   ├ 워크스페이스 검색·증빙 연결
   └ 기업이 BYPRODUCT를 공유 후보로 지정 시 share_status = CANDIDATE
```

## 12. AI 처리·GPU

### 12.1 장비
- 1~2천만 원 범위: RTX 5090급 1~2장 또는 메모리 큰 전문가용 워크스테이션 GPU 1장 (견적 비교)
- 24시간 가동 냉각, 보증 조건, 랙 장착 여부
- 역할: 내부 파이프라인 전용 (비식별·태깅·임베딩·프록시 인코딩·소량 모델 검증)
- 하지 않음: 외부 학습 환경, 전량 실시간 처리
- 업로드는 GPU 처리를 기다리지 않는다 (비동기)

### 12.2 처리량 (가정, 실측으로 갱신)
가정: 카메라 40대(선박 20대×8h×150일 + CCTV 20대×24h×92일) → 연 약 68,000시간. 실효 초당 300프레임.

| 방식 | 연간 프레임 | GPU 소요 |
|---|---|---|
| 전 프레임(30fps) 전량 | 약 73억 | 약 280일 → 불가 |
| 태깅 초당 2프레임 | 약 4.9억 | 약 19일 |
| 임베딩 2초당 1프레임 | 약 1.2억 | 약 5~7일 |
| 비식별: 공유 후보 15% 전 프레임 | 약 11억 | 약 43일 |
| **선별 합계** | | **약 70일** |

벤치마크 항목: 해상도·코덱 × 모델 × 배치 × FPS × VRAM × 지연. 카메라가 늘면 워크스테이션 수평 추가.

### 12.3 우선순위
1. 비식별 (공유·보고 일정) 2. 프록시 (엣지 미생성분) 3. 태깅 4. 임베딩 5. 재처리·검증

### 12.4 비식별 원칙
1. 수집 적법성 먼저. 가공 도구가 최초 수집·목적 외 이용을 정당화하지 않음
2. 얼굴만 가려도 복장·체형·동선으로 재식별 가능
3. 가명정보 ≠ 익명정보. 2026년 3월 31일 전면 개정된 가명정보 처리 가이드라인(위험도 기반) 적용 검토
4. 자동 블러는 누락 가능 → 위험도 기반 검수·수동 예외·처리 이력
5. 원본·가공본 권한 분리, 모델 버전·검수 기록
6. 외부 공동활용은 권리·개인정보 검토 + 기업 승인 + 검수 + 이용자 약정 모두 통과 시
7. 실증특례가 모든 데이터·목적에 포괄 적용된다고 가정하지 않음
8. 처리 이력은 "이력 증명"이지 면책·적정성 보증이 아니다

## 13. 스토리지·인프라·데이터센터

### 13.1 산정식
> 연간 원본(TB) ≈ 대수 × 평균 Mbps × 일 촬영시간 × 연 촬영일수 × 0.45 ÷ 1,000
> 중앙 적재량 = 원본 × collection_mode별 중앙 수집 비율
> 물리 RAW ≈ 필요 USABLE ÷ (보호 효율 × 운영 할당률), 백업은 별도

7일 이상 실측 비트레이트를 우선한다.

### 13.2 용량 용어
RAW(표기 총량) / USABLE(장애보호 후) / 할당 가능(여유·복구 공간 제외) / 백업·DR(별도, 복제는 백업이 아님) — 견적·계약서에 분리 기재

### 13.3 시나리오

| 시나리오 | 조건 | 원본(연) |
|---|---|---|
| S1 제한 실증 | 50대 × 2Mbps × 8h × 120일 | 약 43TB |
| S2 현재 가정 | 선박 20대(4Mbps·8h·150일) + CCTV 20대(2Mbps·24h·92일) | 약 83TB |
| S3 중간 | 30대 × 6Mbps × 12h × 180일 | 약 175TB |
| S4 CCTV 연중 | S2에서 CCTV 365일 | 약 201TB |
| S5 상시 전량(C3) | 100대 × 4Mbps × 24h × 365일 | 약 1.58PB |
| S5-C2 클립만 | S5에서 15%만 클립 | 약 237TB |
| S5-C2 + 전량 프록시 | 위 + 전 영상 프록시(1/8) | **약 434TB** |
| S6 4K 상시 | 100대 × 15Mbps × 24h × 365일 | 약 5.9PB |

**S5-C2 + 전량 프록시의 2년 누적**: 클립 약 474TB + 프록시 약 394TB + 기타 → 논리 약 880TB → 물리 **약 1.9PB** (이레이저 ×1.5, 여유 30%). 100대 규모에서는 선별 수집이어도 **프록시 보존 기간**이 PB 여부를 가른다. 프록시를 6개월만 두면 약 1.25PB로 줄어든다.

### 13.4 S2 기준 2년 필요 용량

| 항목 | 논리 |
|---|---|
| 원본 (12개월 롤링) | 약 83TB |
| 프록시 (1/8, 2년) | 약 20TB |
| 클립·비식별본 (15%, 2년) | 약 25TB |
| 데이터셋·센서·메타 | 약 10TB |
| 합계 | 약 140TB |
| 물리 (×1.5 ÷ 0.7) | **약 300TB** |

### 13.5 PB 구매 판단 규칙
G0 연계 카드로 12개월 필요 USABLE을 산출한 뒤:

| 산출 | 판단 |
|---|---|
| 300TB 이하 | USABLE 300~500TB 시작, 노드 추가 가능 구조 |
| 300TB~1PB | USABLE 1PB급 검토 |
| 1PB 초과 | collection_mode·프록시 보존 기간 재검토 후 재산출 |

**예외**: 후속 증설 예산이 없으면(Q12) 사업기간 내 24~36개월치 확보가 합리적. 이때도 3년 전력·보증, 백업 용량, 빈 디스크의 보증 소진을 함께 따지고, 구매 시점은 실증 개시 직전으로 맞춘다. 증설 발주는 사용률 70% 예측 시점에서 납품 리드타임만큼 앞서 한다.

### 13.6 계층
| 계층 | 미디어 | 용도 |
|---|---|---|
| Hot | NVMe SSD (수십 TB, 부하 시험으로 확정) | 수신 버퍼·처리 작업 공간·DB·최근 데이터 |
| Warm | 엔터프라이즈 HDD (13.5 산출) | 원본·클립·비식별본·데이터셋 |

### 13.7 계층형 백업
| 대상 | 보호 |
|---|---|
| 원본 영상 | 이레이저 코딩 + **기업 현장 사본** (에이전트 기본값: 로컬 삭제 안 함). 약정서에 현장 보관 책임·기간 명시 |
| 메타 DB·감사 로그 | 독립 백업 + 분기 복원 시험 |
| 실증 증빙·보고서 | 독립 백업 |
| 비식별본·데이터셋 | 독립 백업 (재생성 비용 큼) |
| 설정·키·정책 | 독립 백업, 오프라인 보관 |

독립 백업 대상은 수십 TB 수준이다. 삭제 요청 시 활성본·스냅샷·백업의 처리 범위·시차를 정책으로 정한다. RPO/RTO는 G1에서 확정.

### 13.8 초기 구성 (가안)

| 역할 | 수량 | 조달 |
|---|---|---|
| 게이트웨이·포털·업로드 수신 | 2 | 기존 서버 |
| DB (주/대기) | 2 | 기존 서버 + SSD 보강 |
| 처리 워커(CPU) | 2~3 | 기존 서버 |
| 스토리지 노드 | 13.5 산출 (이레이저 4+2면 6노드 이상 권장) | 신규 |
| Hot NVMe | 수십 TB | 신규 |
| GPU 워크스테이션 | 1 | 신규 |
| 백업 서버/스토리지 | 1 | 신규 또는 재활용 |
| 관리·모니터링 | 1 | 기존 서버 |
| 네트워크 | 내부 10Gbps, 관리망 분리, 방화벽 | 신규·보강 |
| 엣지 장비 | 앵커 기업 시범 수량 | 신규 |

기존 서버는 부하시험 후 재활용한다.

### 13.9 회선
- S2 평균 약 21Mbps, S5 상시 전량은 평균 약 400Mbps
- 피크(선박 접안 시 일괄 전송)는 평균보다 훨씬 큼. S2급은 인입 1Gbps를 출발점으로 하되 **실측 후 확정**
- 회선·방화벽 TLS 처리량·NIC·스위치·디스크 기록 속도를 종단 간 검증
- 경보·메타 경로와 대용량 경로 분리

### 13.10 시설
"데이터센터처럼 운영"이지 IDC 신축이 아니다. 설치 장소(출입·소방·온습도), 전력·냉각·UPS, 회선 이중화·망분리, 야간 경보·부품 교체 SLA, 원격 백업·복구 훈련, 가상화·라이선스 지원 종료를 실사하고, 미달이면 IDC 코로케이션과 3년 TCO로 비교한다.

### 13.11 공급사 요구 시트 6종
1. 기업별 일·월 신규 데이터량과 collection_mode별 중앙 전송 비율
2. 3·6·12·24개월 누적량 (원본·프록시·클립·증빙·카탈로그, 보존 정책 반영)
3. RAW / USABLE / 할당 가능 / 백업 분리표
4. 동시 업로드·최대 파일·평균/피크 처리량·노드 장애 시 성능
5. CAPEX와 3년 OPEX
6. 단계별 증설 시나리오와 증설 시 서비스 영향

## 14. 권리·개인정보·보안

### 14.1 약정서 2단 구조 (v0.04 신설)
처리위탁으로 원본을 받으면, 플랫폼은 **위탁 목적(기업을 위한 보관·검색·가공 대행) 안에서만** 처리할 수 있다. 공동활용 데이터셋 구축이나 이용기업 제공은 위탁 범위 밖이므로 별도 근거가 필요하다. 따라서 약정을 둘로 나눈다. (구체적 법적 구성은 자문 필요)

| 단계 | 성격(검토 방향) | 대상 데이터 | 핵심 조항 |
|---|---|---|---|
| 1단 — 수집·관리 약정 | 기업 → 운영기관 처리위탁 | L0·L1 전체 | 위탁 목적·범위, 안전조치, 재위탁 금지·승인, 현장 원본 보관 책임, 반환·파기 |
| 2단 — 공동활용 제공 약정 | 기업이 비식별·검수된 BYPRODUCT 데이터를 공동활용에 제공 | L2~L4 | 제공 범위·목적·기간, 가명/익명 처리 기준, 이용자 약정 연동, 철회·통지, 출처 표기, 수익·성과 배분 |

공통 조항: 원본 권리자·제3자 권리(장비 업체·지자체·발주처), 목적별 허용/금지(공동연구·AI 학습·모델 개선·상용 서비스·외부 판매), 파생물(모델·라벨) 권리, 사고 통지·책임, 감사 권한, 플랫폼 종료 시 반출·파기·이관.

### 14.2 개인정보 점검
- 영상 수집 근거 (설치 목적·안내 등)
- 고정형·이동형 영상정보처리기기 규정 적용 여부 (선박·드론 카메라)

- 필요 시 데이터안심구역·개인정보 안심구역 활용

### 14.3 보안 통제
기업별 테넌트 분리 + RBAC(필요 시 속성 조건), 운영자 최소 권한·고위험 접근 사유·관리자 MFA, 전송·저장 암호화·키 회전, 게이트웨이·WAF·호출 제한·악성코드 검사, 감사 로그 무결성, 원본·공동활용 영역 망·정책 분리, 랜섬웨어 대비 불변 백업 검토, 반출은 승인·만료·워터마크·추적, 저장 위치·재위탁·권한 변경 시 기업 통지

## 18. 산출물·수용시험·KPI

### 18.1 산출물 코드
- **조사**: A01 사전조사표 / A02 기업별 연계 카드 / A03 대표 샘플 목록 / A04 실증지표·보고 양식 매핑표 / A05 기존 장비·시설 실사 보고서
- **표준**: S01 공통 메타데이터 규격 v1.0 / S02 유형별 프로파일 / S03 코드·단위·시간·좌표 규칙 / S04 OpenAPI·JSON Schema·샘플 SDK / S05 에이전트·엣지 연계 규격 / S06 적합성 자동 시험·기업별 연계 승인서 / S07 품질·계보·라벨링 SOP
- **정책**: P01 2단 약정서(수집·관리 / 공동활용 제공) / P02 개인정보·영상정보 적법성 검토표 / P03 등급·보존·삭제·철회·감사 정책 / P04 장애·침해·복구·기업 통지 절차
- **인수**: 서비스·에이전트·관리화면·Runbook, 데이터 모델·인가 정책·스토리지·키·백업 문서, 기업별 UAT·시험 성적서, RAW/USABLE/할당/백업 구분표·3년 비용표, 교육·운영 전환·종료 시 이관 계획
