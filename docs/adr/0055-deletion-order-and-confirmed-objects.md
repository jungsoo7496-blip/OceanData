# ADR-0055: 삭제는 DB가 받아들인 뒤에 객체를 지우고, 못 지운 객체는 증명하지 않는다

- 상태: accepted
- 날짜: 2026-11-12
- 관련: 08번 요구사항 4.1·5.1, ADR-0033(클립 삭제), ADR-0044~0046(업로드 정리·삭제 중 업로드), 지시서 12번 클립·업로드 검토 F1·F5·F6

## 맥락

삭제(`retention.delete_assets`)는 저장소 객체를 먼저 지우고 그 뒤에 삭제 증명 행을 넣었고, 객체 삭제 오류는 모두 삼켰다(`except Exception`).
독립 검토(지시서 12번)가 재현한 결과:

- 증명 행이 DB 제약에 걸리면(사유에 NUL이 있으면 PostgreSQL 텍스트에 저장할 수 없다) 요청은 400이고 DB는 되돌아가는데 **객체는 이미 사라진 뒤**였다.
  자산은 READY_PRIVATE로 살아 있고 다운로드 URL은 없는 객체를 가리켰다. 감사·커밋 같은 뒤따르는 실패도 같다.
- 저장소가 오류를 내면(장애·시간 초과) 오류를 삼킨 채 **'지웠다'는 삭제 증명**을 발급하고 `storage_key`를 비웠다. 객체는 남았고 다시 지울 단서가 없었다.
  삭제 증명은 법적 증빙(T15)이라 이쪽이 더 나쁘다.
- 법적 보류(`set_legal_hold`)는 자산 행을 잠그지 않아, 보류 처리 중에 시작한 삭제가 먼저 끝나면 이미 삭제·증명된 자산에 보류가 '성공'했다.
- 바이너리 없는 C0 자산에 업로드 세션을 열었다가 취소하면 `storage_key`가 남아, 이후 삭제 증명에 만들어진 적 없는 객체가 올랐다(ADR-0046이 피하려던 일).
- 보존 만료 실행(`execute_expired`)은 모든 기관을 한 트랜잭션으로 처리해, 뒤 기관의 실패가 앞 기관의 DB 변경을 되돌렸다(객체는 이미 지워진 뒤).

## 결정

1. **순서: DB 변경 → 증명 행 flush → 객체 삭제.** `delete_assets`는 먼저 자산 삭제 표시·쿼터·증명 행을 만들고 `flush`한다. DB가 받아들이지 않으면 여기서 멈추고 객체는 그대로다.
   그다음 객체를 지운다.
2. **지웠다고 확인된 객체만 '지운 것'이다.** 삭제 호출이 실패하면 `head_object`로 실제로 없는지 확인한다. 없으면 성공(이미 지워졌다), 있거나 확인할 수 없으면 실패다.
   하나라도 실패하면 `DeletionStorageFailed`를 내고, 요청은 **503 `STORAGE_UNAVAILABLE` + `Retry-After`** 로 끝나며 트랜잭션이 되돌려져 자산·쿼터·증명은 그대로다.
   객체 삭제는 멱등이라 같은 요청을 다시 보내면 이미 지운 객체는 '이미 없음'으로 넘어가고 나머지를 이어서 지운다.
3. **바이너리가 없는 자산에는 지울 객체가 없다.** 삭제는 `has_binary`인 자산만 객체 목록·쿼터에 넣고, 업로드 취소로 C0 자산으로 되돌릴 때 `storage_zone`·`storage_key`를 비운다.
4. **보존 만료는 기관마다 SAVEPOINT.** 저장소 삭제가 실패한 기관은 그 기관의 DB 변경만 되돌리고 로그(`retention_delete_failed`)와 운영자 알림(`retention.delete_failed`)을 남긴 뒤 다음 기관으로 간다.
   그 자산은 살아 있고 만료 상태라 다음 실행이 이어서 지운다.
5. **법적 보류도 삭제와 같은 순서로 자산 행을 잠근다**(`lock_live`). 겹치면 먼저 잡은 쪽이 끝난 뒤 다른 쪽이 최신 값으로 판단한다: 보류가 먼저면 삭제는 409, 삭제가 먼저면 보류는 404.

버린 대안:
- *삭제 표시와 증명을 먼저 커밋하고 객체는 커밋 뒤에 재시도 목록으로 지우기(2단계, outbox)*: 가장 견고하지만 재시도 표(마이그레이션)와 정리 작업이 필요하고, 증명이 '지워짐'을 말하는 시점이 객체 삭제 확인보다 앞서게 되어
  **삭제 증명의 의미가 바뀐다**. 증명의 법적 의미는 사람이 정해야 하므로 제안만 한다(아래).
- *사유에 제어 문자를 막는 패턴(계약 변경)*: 입력 검증만으로는 감사·커밋 같은 다른 실패를 막지 못한다. 순서를 바꾸면 NUL도 객체를 건드리기 전에 400이 된다.

## 결과

좋아지는 점: DB가 거부한 삭제는 객체를 지우지 않는다. 저장소 장애 중 삭제는 거짓 증명 대신 503이고 재시도하면 이어서 끝난다. 보류와 삭제의 경합이 한쪽으로 정리된다.
C0의 유령 객체가 증명에서 사라진다. 한 기관의 저장소 문제가 다른 기관의 보존 만료를 되돌리지 않는다.

감수할 점:
- 객체 삭제는 여전히 요청 트랜잭션이 커밋되기 전에 일어난다. 그 사이(드문 직렬화 실패·연결 끊김)에 실패하면 객체는 지워졌는데 자산은 살아 있다. 같은 요청의 재시도가 낫게 한다(삭제는 멱등).
  그동안 `download-url`은 없는 객체를 가리킬 수 있다.
- 여러 자산 삭제(회차)에서 중간 객체가 실패하면 앞서 지운 객체는 이미 사라진 채 모든 자산이 살아 있다(위와 같은 이유, 재시도로 해소).
- `ASSET_DELETED` 감사는 별도 연결로 바로 커밋된다(다른 감사와 같다). 커밋 실패 시 감사에는 남고 삭제는 되돌아간다 — 재시도가 같은 감사를 한 번 더 남긴다. 감사를 요청 트랜잭션에 묶는 일은 감사 해시 체인 잠금을
  요청 끝까지 쥐게 하므로 따로 판단한다.
- 쿼터 `quarantine_bytes` 정합(격리 이동 실패 뒤 삭제), 취소·만료 정리의 저장소 오류 삼킴은 이 ADR의 범위 밖이다(`docs/review-2026-11-12/README.md`).

**사람이 정할 것**: 삭제 증명을 '객체 삭제 확인 뒤'에만 발급할지(지금), 아니면 삭제를 2단계로 하고 증명에 '삭제 요청됨'과 '삭제 확인됨' 시각을 따로 둘지.

되돌리는 방법: `delete_assets`의 flush·객체 삭제 순서를 이전으로 되돌리면 된다(마이그레이션·계약 구조 변경 없음). 계약 문구(삭제·법적 보류 설명)는 이 동작을 말하므로 함께 되돌린다.

시험: `tests/integration/test_deletion_safety.py` 7개 — NUL 사유가 객체를 건드리지 않음, 저장소 실패가 503이고 증명·자산·쿼터 그대로이며 재시도가 끝냄, 회차 삭제의 중간 실패, 한 기관 실패가 다른 기관 삭제를 되돌리지 않음,
법적 보류와 삭제 경합, C0 취소 뒤 증명에 유령 객체 없음, 이미 저장된 낡은 `storage_key`. 수정 전 코드에서 7개 모두 실패하는 것을 확인했다.
