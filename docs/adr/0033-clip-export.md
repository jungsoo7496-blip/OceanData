# ADR-0033: 구간 클립 내보내기 — 작업 큐 재인코딩, 파생 자산 CLIP, 같은 실패는 재시도하지 않음

- 상태: accepted
- 날짜: 2026-11-05
- 관련: 09번 요구사항 7.2·작업 9, 05번(작업 큐·파생 자산·계보), domain.md 2장(바이너리는 자기 기관)·3장(variant CLIP), ADR-0002,
  08번(쿼터·삭제·보존 만료 — 아래 '갱신')

## 맥락
요구사항 7.2는 "구간을 선택해 클립 내보내기를 요청하면 원본에서 클립을 만드는 작업을 등록하고 결과를 파생 자산으로 연결"이다.
정할 것: 자르는 방식(스트림 복사 / 재인코딩), 결과 자산의 속성, 사용자가 진행 상황을 보는 방법, 다시 해도 같은 실패의 처리.

## 결정
1. **API**: `POST /v1/assets/{id}/clips {start_s, end_s, reason?}` → 202 `ClipJob`, `GET /v1/assets/{id}/clips` → 최근 요청부터.
   권한 `asset:clip` = 자기 기관 ORG_ADMIN·ORG_MEMBER (운영자·관리기관·기계 주체 불가, 다른 기관 자산은 403/404).
   원 영상은 VIDEO·ORIGINAL 또는 CLIP·바이너리 있음·REGISTERED/PROXIED/READY_PRIVATE·길이(video_ext.duration_s) 확인됨 — 아니면 409.
   구간은 end > start, end ≤ 영상 길이, 길이 ≤ `CLIP_MAX_S`(기본 3600초) — 아니면 400. 같은 구간 작업이 대기·실행 중이면 그 작업을
   돌려준다(두 번 누름). 새로 등록할 때만 감사 `CLIP_EXPORT_REQUESTED`(구간·작업 ID·사유).
2. **자르는 방식 = 재인코딩**: `ffmpeg -ss <start> -i 원본 -t <길이>` + libx264(`CLIP_CRF`=18, veryfast, yuv420p), 음성 AAC 128k,
   메타데이터 제거, faststart. 입력 앞 -ss는 가까운 키프레임부터 디코딩해 시작 전 프레임을 버리므로 프레임 단위로 정확하다.
   버린 대안 — 스트림 복사(`-c copy`): 파일이 앞 키프레임부터 시작하고 길이가 요청보다 길다(합성 4초 영상의 1.0~2.5초 구간:
   복사 1.667초, 재인코딩 1.533초 = 23프레임). 첫 화면은 편집 목록(edit list)으로 맞추지만 이를 무시하는 도구에서는 앞 프레임이
   보이고, 증빙·데이터셋은 요청 구간과 같아야 한다. 감수: CPU 인코딩 시간, CRF 18의 미세한 화질 손실. GPU 인코더는 쓰지 않는다
   (프록시만 GPU 선택) — 필요하면 나중에 추가.
3. **결과 = 파생 자산**: `create_derived`(variant=CLIP, PRIVATE, 원 영상의 data_role·민감도·개인정보 상태·보존 정책 상속,
   계보 relation=CLIP, 무결성 로그). `provenance.clip_range_s=[start, end]`(계약 common.schema에 추가)·`job_id`·도구 버전,
   촬영 시각은 원 영상 시작 + 구간(원 영상이 미상이면 미상), `video_ext`는 결과를 ffprobe로 다시 읽는다. 공유는 13번 규칙 그대로.
4. **작업**: `clip_export`(우선순위 70 = 썸네일 다음, CPU, 임대 2시간, 최대 3회 — 마이그레이션 0021, down은 대기 작업·정책 삭제).
   원 영상이 그 사이 격리·삭제됨(`SOURCE_UNAVAILABLE`)·인코딩 실패(`CLIP_ENCODE_FAILED`)는 다시 해도 같으므로 새 공통 예외
   `PermanentJobError`로 바로 FAILED(시도 1회, 코드는 jobs.last_error_code). 다른 작업 유형도 쓸 수 있다.
5. **진행 상황**: 별도 표를 만들지 않고 `QueuePort.jobs_for_asset`로 jobs 표를 읽는다. DONE이면 결과 자산을 `provenance.job_id`로,
   없으면 같은 구간으로 찾는다(같은 결과는 체크섬이 같아 create_derived가 기존 자산을 돌려준다). 결과가 지워졌으면 비운다.

## 결과
- 좋아지는 점: 요청 구간과 정확히 같은 클립이 계보·출처와 함께 남아 증빙 인용(10번)·데이터셋(13번)에 그대로 쓸 수 있다.
  화면은 프록시 재생 위치로 구간을 정하고 5초마다 상태를 다시 읽는다.
- 감수할 점: 짧은 구간도 원본 전체를 작업 디스크로 받아 온다(대용량 원본은 객체 저장소 범위 읽기로 줄일 수 있음 — 확인 필요).
  재인코딩 시간은 구간 길이에 비례한다(운영 하드웨어 실측 필요).
- 되돌리는 방법: 0021 down, 경로·권한·작업 등록 제거. 만든 클립 자산은 일반 파생 자산이라 그대로 남는다.

## 갱신 (2026-11-05, 보안 검토: 쿼터·기관별 대기 한도·감사 원자성·삭제와 겹침)
검토에서 세 가지가 나왔다. 계약 먼저 고쳤고(클립 POST의 409·429 설명, `ClipRequest.reason` pattern, `ClipJob.error_code`),
마이그레이션은 없다. 작업 정책(0021, 우선순위 70)은 그대로다 — 운영자가 `/v1/job-policies`에서 바꿀 수 있다.

1. **쿼터·기관별 한도** (검토 A, 재현: 사용량 = 쿼터인 기관의 요청 4건이 모두 202, 쿼터 0에 사용량 288,914바이트.
   같은 구간만 막아 1 ms씩 다른 3600초·CRF 18 작업을 얼마든지 쌓을 수 있었다)
   - 요청: 업로드 예약과 같은 규칙·같은 오류(`Quota.require_room` — 저장+격리+예약+신청 백업, 409 QUOTA_EXCEEDED, 본문
     quota_bytes·usage_bytes). 클립 크기는 만들어 봐야 알므로 요청 때는 여유가 1바이트도 없을 때만 거절한다.
   - 기관의 대기·실행 중(QUEUED·RUNNING, 재시도 대기 포함) 클립 작업이 `CLIP_MAX_PENDING_PER_ORG`(기본 3, HW-3 설정) 이상이면
     429 RATE_LIMITED + Retry-After(30초), 본문 pending_jobs·limit. 기다리면 풀리는 상태라 409가 아니라 429로 했다 — 예제
     클라이언트·자동 연계는 Retry-After 뒤 다시 보낸다. 세기와 등록은 기관 쿼터 행 잠금으로 직렬화해 동시 요청으로 넘지 않는다.
     같은 구간을 다시 누르면 한도·쿼터와 상관없이 진행 중인 그 작업을 돌려준다.
   - 작업: 클립 크기로 올리기 전에 확인하고(넘으면 올리지 않음), 기록할 때 쿼터 행을 잠근 뒤 실제 크기로 다시 확인한다
     (`pipeline.record_derived(enforce_quota=True)`). 넘으면 클립을 남기지 않고 바로 FAILED(`QUOTA_EXCEEDED`), 올린 객체는 지운다.
   - 프록시·썸네일·비식별본은 쿼터를 예약한 업로드에서 원본마다 정해진 만큼만 나오므로 지금처럼 확인 없이 사용량에 더한다.
2. **작업 등록과 감사의 원자성** (검토 B, 재현: 사유에 NUL → 감사 INSERT 실패로 400인데, 먼저 커밋된 작업은 대기열에 남아 실행됨.
   다시 보내면 같은 작업으로 묶여 감사는 끝내 없었다)
   - `QueuePort.enqueue(connection=)`·`count_active(connection=)`: 작업 행을 요청 트랜잭션에 넣고, 감사도 `connection=`으로 같은
     트랜잭션에 남긴다(정책 초안과 같은 방식). 핸들러가 202를 돌려주기 전에 커밋한다 — `get_db`는 응답을 보낸 뒤에 커밋하므로
     그대로 두면 커밋 실패가 202 뒤에 숨는다.
   - 계약 `ClipRequest.reason`에 제어 문자 금지 pattern `^[^\x00-\x1f\x7f]*$`(카탈로그 이름과 같은 표기), 서버 모델도 같다 → 400 `/reason`.
3. **원 영상 삭제와 겹칠 때** (검토 C: 작업은 원 영상을 잠그지 않고 확인한 뒤 클립을 올리고 기록했고, 삭제는 잠그지 않고 파생본을
   찾았다. 그 사이에 삭제·보존 만료가 끼면 삭제 증명에 없는 클립이 남았다)
   - 작업(`clips.store_clip`): 객체는 잠그지 않고 먼저 올린다(오래 걸리는 전송 동안 원 영상 행을 잠그지 않는다). 기록 트랜잭션에서
     원 영상 행을 `FOR UPDATE`로 잠그고 다시 확인해, 삭제·격리됐으면 FAILED(`SOURCE_UNAVAILABLE`)하고 올린 객체를 지운다.
     `create_derived`를 단계(same_result → new_derived → 객체 저장 → record_derived)로 나눴고 다른 파생 작업의 동작은 같다.
   - 삭제(`POST …/deletion`): `retention.with_descendants(lock=True)` — 원 자산 행을 asset_id 순으로 잠그고 최신 값으로 다시 읽은
     뒤 파생본을 찾고, 계보 단계마다 같은 방식으로 잠근다(클립의 클립도). 작업이 먼저 잠갔으면 삭제는 기다렸다가 그 클립까지 지워
     삭제 증명에 올리고, 삭제가 먼저면 작업이 클립을 남기지 않는다. 기다리는 사이 다른 요청이 지운 자산은 빼고, 단일 자산 삭제가
     그래서 비면 404.
   - 보존 만료(`execute_expired`): 대상 행을 `FOR UPDATE OF assets`·asset_id 순으로 먼저 잠근다. 보존 만료가 파생본을 함께 지우지
     않는 것(파생본은 자기 보존 정책, CLIP은 clip_default)은 그대로다.
   - 잠금 순서: 자산 행을 기관 쿼터 행보다 먼저 잠근다(클립 요청·클립 기록·삭제·보존 만료 — 기존 격리 이동·업로드 검증과 같다).
     클립 기록은 다른 파생 작업처럼 무결성 로그 잠금 다음에 쿼터 행을 잠그고, 같은 트랜잭션의 감사는 맨 마지막에 남긴다.

시험(`tests/integration/test_clips.py`): 요청 쿼터 409·기관별 한도 429·기관 B는 영향 없음·작업이 끝나면 다시 등록, 작업의 쿼터
재확인(올리기 전·기록할 때, 올린 객체 삭제), 사유 제어 문자 400·감사 실패 시 작업 없음, 삭제가 먼저(API 삭제·보존 만료 — 갈고리로
작업의 확인과 커밋 사이에 삭제), 작업이 먼저(삭제가 행 잠금을 기다린 뒤 클립을 삭제 증명에 올림). 각 고침을 되돌리면 해당 시험이
실패함을 확인했다.

결과
- 좋아지는 점: 쿼터가 찬 기관은 클립으로 저장소를 늘릴 수 없고, 한 기관이 긴 재인코딩 작업으로 공용 큐를 채울 수 없다.
  202를 받은 요청에는 언제나 감사가 있고, 삭제 증명에 없는 클립이 남지 않는다.
- 감수할 점: 요청 때는 '여유 0'만 거절하므로 여유가 조금 남은 기관의 작업은 저장 직전에 FAILED(QUOTA_EXCEEDED)가 될 수 있다
  (화면에 원인 표시). 올리기 전 확인과 기록 사이에 쿼터가 차면 한 번 올렸다가 지운다. 삭제 요청은 기록 중인 클립의 커밋을
  기다린다(전송은 잠금 밖이라 짧다). 한도 기본값 3은 실측 전 값이다.
