# ADR-0056: 계약 검증기는 어떤 입력에도 예외 없이, 계약이 정한 값만 통과시킨다

- 상태: accepted
- 날짜: 2026-11-12
- 관련: 03번 요구사항 4·13.2, 10번 요구사항 4.5, ADR-0018(보고서 렌더러), 지시서 12번 검증기·내보내기 검토 1~7

## 맥락

사전 검증 API(`POST /v1/contracts/validate`)와 운영 업로드·관측값·이벤트 API는 같은 함수(`contracts.validate_document`)를 쓴다(요구사항 13.2).
독립 검토가 이 함수와 보고서 내보내기에서 다음을 재현했다.

1. **NaN·±Infinity가 숫자로 통과한다.** 파이썬 JSON 파서가 받아 주고 `jsonschema`의 `number`가 거르지 않는다. 관측값에 저장돼 `value: null, quality_flag: GOOD`(결측 규칙 위반)로 읽히고,
   그 구간을 포함한 보고서 생성은 PostgreSQL이 JSONB의 `NaN`을 거부해 500이 된다.
2. **잘못되었지만 읽히는 입력에서 예외**(→ 500, 인증된 호출자만): `observations`가 숫자, 시각을 UTC로 바꿀 때 넘침(`0001-01-01T00:00:00+23:59`), 위치 좌표가 배열이 아님·400자리 정수,
   9천 단계 중첩(jsonschema의 오류 메시지 repr이 재귀 한도를 넘는다).
3. **운영 이미지가 개발 환경보다 약하다.** `format: date-time`은 선택 패키지(rfc3339-validator)가 있어야 검사되는데 운영 의존성에는 없고 개발 환경에는 간접 설치돼 있다. 운영에서는
   `2026-13-02T00:00:00Z`가 통과해 뒤에서 `TimeRuleError`(→ 500)가 났다.
4. **`^…$` 패턴이 끝의 개행을 통과시킨다.** 파이썬 `re`의 `$`는 끝 개행 앞에도 맞는다. 공개 계약은 ECMA-262라 아니다. 체크섬에 `\n`을 붙인 값이 검증을 통과해 DB 길이 오류(500)나
   저장소 거부(503, 에이전트가 계속 재시도)가 났다.
5. **문제 목록이 한없이 커진다**(좌표가 문자열이면 글자마다 문제 하나: 20KB 요청에 2.6MB 응답).
6. **XML이 담을 수 없는 제어 문자**(U+0001~0008·0B·0C·0E~1F 등)가 보고서 문구에 있으면 XLSX 내보내기는 예외(500)이고 HWPX는 파서가 못 읽는 파일을 200으로 보낸다.
   승인·제출된 버전은 고칠 수 없어 그 내보내기가 계속 깨진다. HWPX 양식의 속성 값 안에 값이 들어가면 따옴표로 속성을 끼워 넣을 수 있다.

## 결정

1. **검증기를 한 곳(`contracts.contract_validator`)에서 만든다.** 쿼리 매개변수 검증(`contract_query`)도 같은 검증기를 쓴다.
   - `number`는 유한한 수만 받는다(bool·NaN·±Infinity 제외). jsonschema는 `$ref`로 내려갈 때 하위 문서의 `$schema`를 보고 표준 검증기 클래스로 바꾸므로(우리 설정이 꺼진다),
     검증용 스키마 사본에서 `$schema`를 뺀다. 클라이언트에 내려주는 스키마(`bundle`)는 바뀌지 않는다.
   - 검증용 사본에서만 패턴 끝의 `$`를 `\Z`로 바꾼다(이스케이프·문자 클래스 안은 그대로). 공개 스키마는 ECMA-262 문법 그대로다. 계약 패턴은 `\d`·`\w` 없이 `[0-9]` 등을 쓰므로 다른 차이는 없다.
   - `date-time`은 우리 구현이다: RFC 3339 형태 + 서버가 UTC로 바꿀 수 있는 값(`parse_rfc3339`와 같은 기준). 윤초(`:60`)와 UTC 변환 넘침은 받지 않는다. 선택 패키지에 기대지 않으므로 운영과 개발이 같다.
2. **예외 대신 문제로.** `check_location`·`_observation_problems`는 어떤 JSON에도 문제 목록을 돌려준다(배열이 아닌 좌표는 그 자리 하나만, 큰 정수·bool은 잘못된 좌표). `parse_rfc3339`는
   UTC 변환 넘침을 `TimeRangeError`로, 오프셋 없음을 `NoOffsetError`로 낸다(둘 다 `TimeRuleError`). 관측 항목은 오프셋 없음에만 `timezone_required`를 붙이고, 형식 오류는 스키마의 구체적 오류를 그대로 둔다.
   중첩이 64단계를 넘는 문서는 재귀하지 않는 검사로 `schema.depth` 하나만 돌려준다.
3. **문제 목록은 앞의 100개와 안내 하나.** `schema.truncated`(WARNING)는 유효성에 영향을 주지 않는다. 오류가 하나라도 있으면 목록에 오류가 남는다.
   예외는 항목마다 거부 사유를 정하는 관측값 배치다: 목록을 자르면 뒤쪽 잘못된 항목이 검사 없이 정규화로 넘어가므로 `validate_document(..., limit=ITEM_PROBLEM_LIMIT)`(5만, 항목 수 한도 5000이라 방어용)로 모으고,
   그래도 잘렸으면 배치 전체를 400으로 거부한다. 응답에 담는 400 본문(`_problems_to_400`)은 어느 경우든 100개와 안내 하나다.
4. **내보내기는 XML이 담을 수 없는 문자를 뺀다.** XLSX는 렌더링 모델의 모든 문자열에서, HWPX는 치환 값에서 뺀다(보이지 않는 제어 문자라 내용은 달라지지 않는다. 탭·줄바꿈·CR은 남긴다).
   HWPX 치환은 `"`·`'`도 엔티티로 바꾼다. 입력 단계에서 막지 않는 이유: 이미 저장된 승인·제출 버전도 내보내져야 한다.

버린 대안:
- *`jsonschema[format-nongpl]`/rfc3339-validator를 의존성에 추가*: 라이선스·OSS-CANDIDATES 검토와 ADR이 필요하고, 한 형식을 위해 패키지 묶음을 들이는 것보다 서버가 이미 쓰는 시각 파서와 같은 기준을 직접 쓰는 편이 일관된다.
- *전역 `try/except Exception`으로 500 막기*: 버그를 입력 오류로 숨긴다. 총괄성은 명시적 가드와 속성 시험(`hypothesis`)으로 확인한다.
- *입력 단계에서 제어 문자 거부(계약 패턴)*: 기존 저장분의 내보내기를 고치지 못한다.

## 결과

좋아지는 점: 사전 검증이 실제 결과를 예측한다(운영과 개발이 같다). 잘못된 입력은 500이 아니라 400/`valid:false`다. NaN이 저장·전파되지 않는다. 응답 크기가 제한된다. 보고서 내보내기가 사람이 쓴 글 때문에 깨지지 않는다.

감수할 점:
- `date-time`을 더 엄격히 본다(윤초·넘침 거부, 오프셋은 `±hh:mm`·`Z`만). 계약 예시와 기존 시험은 모두 통과한다.
- 문제 목록이 100개를 넘으면 뒤는 보이지 않는다(고치고 다시 검사하면 나머지가 나온다).
- 요청 본문 크기 제한은 앱에 없다(웹 프록시 `nginx.conf`가 `/v1/`에 20m). 가까운 원인인 문제 목록 증폭은 막았지만 큰 문서 하나의 CPU·메모리는 프록시 설정에 기댄다.
- 관측값 배치의 항목 단위 값 오류는 여전히 항목별 REJECTED 사유(`MISSING_FLAG_MISMATCH` 등)로 나간다(요구사항 1.3). 사유 이름은 도메인 코드라 바꾸지 않는다.
- 남은 지적(HWPX 양식 인코딩·ZIP 경로 검사, PDF 렌더 비용, 이벤트 문서의 불필요한 `unevaluatedProperties` 오류, `observations[].location`의 도메인 검사)은 `docs/review-2026-11-12/README.md`.

되돌리는 방법: `contract_validator`가 만드는 검증기를 표준 `Draft202012Validator`로 되돌리면 값 검사가 이전으로 돌아간다. 계약 파일은 바뀌지 않았다.
