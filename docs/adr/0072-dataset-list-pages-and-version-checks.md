# ADR-0072: 데이터셋 목록의 쪽 나눔과 버전 만들기 입력 검사

- 상태: accepted
- 날짜: 2026-11-12
- 관련: 13번 요구사항 5.1·5.3·6.1·7.1, 13번 작업 32(큰 버전), api-conventions.md(목록 커서·오류 코드), ADR-0053(요청 트랜잭션), 2026-11-12 계약 점검 S01·S03·S04·S05

## 맥락

2026-11-12 계약 점검에서 데이터셋 버전·목록·계보의 빈틈 네 가지가 나왔다.
1. **S01 큰 버전의 데이터 카드**: 항목이 `DATASET_SYNC_MAX_ITEMS`(기본 200)를 넘으면 `start_build`가 자산 조건만 보고 데이터 카드는 검사하지 않았다.
   필수 항목이 빠진 카드도 202 BUILDING으로 받았고, 그동안·그 뒤 운영자의 `GET /v1/datasets/{id}`·`GET /v1/datasets`는 그 카드를 `data_card`로 내보내
   `Dataset` 스키마를 어겼다. 작업은 나중에 요청 때 이미 있던 결함을 "그사이 조건이 바뀐" FAILED로 알렸다. 요청 안에서 만드는 버전은 같은 카드에 422를 준다.
2. **S03 목록**: 계약 `listDatasets`는 `limit`(기본 50, 최대 500)·`cursor`를 받는데, 서버는 값의 형식만 검사하고 모든 데이터셋을 한 번에 돌려주며
   `next_cursor`는 늘 null이었다. 이용기관에게 보일지는 `visible_versions`(게시·L3 이상·READY)가 파이썬에서 판정하므로, SQL에서 자르고 나서 거르면 쪽이 짧아지고
   커서가 어긋난다.
3. **S04 계보의 409**: BUILDING·FAILED 버전의 계보는 13번 작업 32대로 409 CONFLICT인데 계약 응답 목록에 409가 없었다.
4. **S05 item_asset_ids**: 계약은 `asset_id` 형식·`uniqueItems`인데 서버 모델은 `list[str]`이었다. 같은 ID 두 번은 조용히 합쳐 201(멱등 기록 본문에는
   중복 그대로), 형식이 아닌 값은 공유 조건 검사까지 가서 422 RULE_VIOLATION이 됐다.

## 결정

1. **S01**: `start_build`가 자산 조건(`_validate`) 다음, BUILDING 행과 `dataset_build` 작업을 만들기 전에 데이터 카드만 매니페스트 계약의
   `#/properties/data_card`로 검사한다(`_check_card`). 포인터는 `/data_card`부터 붙여 요청 안 경로(`_materialize`, 매니페스트 전체 검사)와 같은 422 본문이 된다.
   버린 대안: 빈 `items`로 매니페스트 뼈대를 만들어 전체를 검사하기 — 매니페스트 계약이 `items`에 `minItems: 1`을 두어 카드와 상관없는 오류가 섞인다.
2. **S03**: `page_params`로 `limit`·`cursor`를 받고 `dataset_id` 순으로 나눈다. 커서는 마지막으로 **돌려준** 데이터셋 ID(`pagination.encode_cursor`).
   한 번에 `limit+1`개씩 읽으며 이용기관에게 보이는 버전이 없는 데이터셋은 건너뛰고, 쪽이 차고도 보이는 데이터셋이 하나 더 있을 때만 `next_cursor`를 준다.
   제공기관·운영자는 SQL에서 이미 걸러져 같은 코드에서 한 번 읽고 끝난다.
   버린 대안: 이용기관 조건을 SQL로 옮기기 — 버전 등급은 항목의 '현재' 등급 중 가장 낮은 것이고 지워진 항목은 PRIVATE로 센다(domain.md 4장,
   `rules.dataset_scope`). 같은 규칙을 SQL로 다시 쓰면 규칙이 두 곳에 생겨 어긋날 수 있다. 안 보이는 데이터셋이 아주 많으면 한 쪽을 위해 많이 읽지만,
   데이터셋 수는 자산 수보다 훨씬 적다.
   웹(운영 콘솔 데이터셋·이용기관 카탈로그)은 `next_cursor`를 따라가지 않으므로 `?limit=500`(계약 최대)으로 부른다. 지금처럼 한 번에 모두 보인다.
3. **S04**: 동작은 그대로 두고 계약만 고친다. `getDatasetVersionLineage`에 `'409': Conflict`를 넣고 설명에 "READY만, BUILDING·FAILED는 409,
   볼 수 없는 버전은 상태와 관계없이 404"를 적는다(범위 검사 404가 상태 검사보다 먼저라 상태가 새지 않는다).
4. **S05**: 항목마다 `asset_id` 패턴(common.schema.json과 같은 식)을 모델에서 검사해 400과 `/item_asset_ids/<i>` 포인터를 준다. 중복은
   `run_idempotent` 전에 400 VALIDATION_ERROR(`code: unique`, 다시 나온 자리마다, 최대 100개)로 거부한다 — 웹훅 `event_types`·재처리 `steps`와 같은 방식.
   형식이 맞는데 없는 자산은 지금처럼 422 RULE_VIOLATION.
   버린 대안: pydantic `field_validator`로 중복 거부 — 포인터가 `/item_asset_ids` 하나로만 나와 어느 자리인지 알 수 없다.
5. 바꾸지 않은 것: `dataset_view`의 `data_card`는 지금처럼 운영자에게 가장 최근 버전(BUILDING·FAILED 포함)의 카드다. 최신 READY 버전의 카드로 바꾸는 것은
   운영자가 보는 내용이 바뀌는 일이라 이번 범위 밖이다. 1번 뒤로는 새로 받는 카드가 모두 계약을 통과한다.

## 결과

좋아지는 점: 두 경로가 같은 카드에 같은 422를 주고, 틀린 카드로 BUILDING 버전·작업이 생기지 않는다. 운영자의 데이터셋 조회가 계약을 지킨다.
목록이 계약대로 나뉘어 응답 크기가 한도 안에 있고, 이용기관 쪽도 짧거나 빈 쪽 없이 이어진다. 계보 409가 계약에 적힌 응답이 된다.
중복·형식 오류가 400으로 바로 보이고, 만든 버전과 멱등 기록 본문이 어긋나지 않는다.

감수할 점: 전에는 받던 요청(큰 버전의 틀린 카드, 중복 ID)이 422·400이 된다 — 계약이 원래 허용하지 않던 입력이다. 목록을 `limit` 없이 부르던
클라이언트는 이제 50개씩 받는다(웹은 500으로 고쳤고, 데이터셋이 500개를 넘으면 웹도 쪽 넘김이 필요하다). 수정 전에 큰 버전 경로로 받아 둔 틀린 카드가
운영 DB에 있으면 그 데이터셋의 운영자 조회는 여전히 계약을 어긴다(있는지 확인 필요, 새 버전으로 다시 만들면 된다).

되돌리는 방법: `services/datasets.py`의 `_check_card` 호출, `api/datasets.py`의 `_dataset_page`·`page_params`·`ASSET_ID`·`_duplicate_items`를 되돌리고
웹 `Sharing.tsx`의 `?limit=500`을 지운다. 계약의 계보 409 줄을 되돌리면 생성 클라이언트를 다시 만든다. 마이그레이션 없음.

## 시험

계약 검사, 중복·형식 오류 ID(400·포인터, 작업 큐 경로 포함, 멱등 키 남지 않음, 없는 자산 422), 운영자 목록 51개(기본 50, 20씩 이어 읽기),
이용기관 목록(앞뒤에 안 보이는 데이터셋이 있어도 1개·2개 쪽이 정확). `test_dataset_build.py`의 계보 409에도 계약 검사를 붙였다.
