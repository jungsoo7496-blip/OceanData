# ADR-0040: 뜨거운 조회·폴링 경로의 인덱스 (작업 꺼내기·주기 감시·목록)

- 상태: accepted
- 날짜: 2026-11-05
- 관련: 05번 요구사항 1.2(작업 큐), 04번 요구사항 3.3(만료 업로드 정리), 11번 요구사항 2.1·5.1(감시 규칙·실패 원인),
  07번 요구사항 8.1·09번 요구사항 5.2(관측값 시간축·회차 필터), 09번 요구사항 2.1(대시보드 처리 대기·격리),
  tech.md HW-8, ADR-0002·ADR-0014(PostgreSQL 작업 큐), ADR-0036(계층 이동), 마이그레이션 0024

## 맥락

쉬지 않고 도는 조회(워커의 작업 꺼내기, 정비·감시·웹훅 주기, 대시보드가 1분마다 부르는 수집 상태, 목록·검색)를 실데이터 규모에서
`EXPLAIN (ANALYZE, BUFFERS)`로 봤다. 기준 문서·스펙에는 행 수 가정이 없어(기준선 13장은 TB 단위만) 아래 규모를 정했다.
기준선 13장 S2(카메라 40대: 선박 20대 × 8시간 × 150일 + CCTV 20대 × 24시간 × 92일 ≈ 연 6.8만 시간, 10분 단위 파일)를
기관 3곳(50·35·15%)에 나눈 약 10개월치(2026-01-01 ~ 11-05)다. 모두 합성 데이터(`generate_series`)다.

| 표 | 행 수 | 비고 |
|---|---|---|
| assets | 500,000 (살아 있는 것 490,126) | 원본 영상 42%·센서 파일 10%·이미지 2%·파생(프록시·썸네일 등) 46%, 격리 1%, 최근 36시간은 일부 처리 중 |
| jobs | 1,087,987 (끝남) + 대기 상황 2가지 | 끝난 작업을 지우지 않아 업로드 파일당 약 3건(무결성 → 메타 → 환경 결합) 쌓인다. 평시: 대기 160(그중 재시도 대기 100)·실행 9. 몰림: 대기 40,160 (2주 항해 뒤 접안 업로드 ≈ 1.3만 파일 × 3단계) |

| audit_log | 1,500,000 | |
| events | 200,000 | |
| webhook_deliveries | 150,000 | 보낼 것 25, 재시도 대기 275 |
| 그 밖 | sessions 1,202 · devices 84 · tier_moves 3,005 · incidents 3,000 · datasets 200 / versions 400 / items 39,887 | |

환경: PostgreSQL 16.10 기본 설정(shared_buffers 128MB, work_mem 4MB, random_page_cost 4, 병렬 작업자 2), 4코어 공유 호스트, DB 약 3.2GB.
측정: 앱의 실제 함수(API 처리기·서비스·`PgQueue`)를 불러 pg8000으로 나가는 SQL과 매개변수를 그대로 잡고, 같은 매개변수로
`EXPLAIN (ANALYZE, BUFFERS)`를 한 번 데운 뒤 7번 돌린 실행 시간의 중앙값. 버퍼 수(shared hit + read)는 캐시와 무관한 작업량이다.
병렬 순차 탐색은 같은 계획이어도 실행마다 2~4배 흔들렸다(OS 캐시·작업자 기동) — 아래 표의 '전'은 마지막 측정값이고 대괄호에 다른 측정값을 적었다.

찾은 것:
1. **작업 꺼내기** (`pg_queue.claim`, 워커마다 계속): `ORDER BY priority DESC, run_after, created_at`인데 `ix_jobs_claim`은
   (status, priority, run_after) 모두 오름차순이다. 거꾸로 읽으면 run_after 방향이 반대라 최상위 우선순위 묶음 전체를 읽어 정렬한다(증분 정렬).
   평시에는 0.1ms지만 몰림(최상위 우선순위 1만 건)에서는 꺼낼 때마다 31ms·버퍼 2.1만 — 대기가 길수록 꺼내기가 느려져 적체를 더 키운다.
2. **만료 업로드 정리** (5분마다): `expires_at` 인덱스로 '지난' 쪽을 읽는데 끝난 업로드도 모두 기한이 지났다 → 26.5만 행을 걸러 낸다.
3. **감시 규칙** (1분마다): 수집량 급감·격리 급증·용량 예측·회차 무수집이 `ingested_at >= …`로 최근 자산을 세는데 ingested_at으로 시작하는
   인덱스가 없다 → 용량 예측은 자산 표 전체 병렬 순차 탐색, 회차 무수집은 진행 중 회차마다 기관 자산 25만 건 비트맵.
   업로드 실패율(`created_at >= …`)도 업로드 표 전체를 읽는다.
4. **수집 상태 API의 최근 실패 원인** (대시보드가 1분마다): 오류 코드가 있는 업로드를 `updated_at`으로 거르는데 인덱스가 없다 → 업로드 표 전체.
5. **대시보드 처리 대기·격리 목록** (`/v1/assets?ingest_status=…&limit=500`, asset_id 커서 순서): 처리 대기 자산은 가장 최근 것이라
   기본키 순서로 읽으면 끝까지 가야 한다. 처리 대기 1만 건에서 357~391ms(버퍼 6.8만).
6. **관측값 시간축** (기관 전체·회차 필터): 두 인덱스가 (기관, 장비, 항목, …)로 시작해 시각 범위만으로는 월 파티션 전체를 읽는다.

## 결정

마이그레이션 0024(down 포함)로 인덱스만 바꾼다. 표·API·결과와 순서는 그대로다(시험으로 확인).

| 인덱스 | 쓰는 조회 |
|---|---|
| `ix_jobs_claim_queued` jobs (priority DESC, run_after, created_at) WHERE status = 'QUEUED' | `pg_queue.claim` — 꺼낼 순서 그대로 읽어 첫 행에서 멈춘다. `ix_jobs_claim`은 RUNNING·FAILED 조회(임대 회수·실패 원인)에 그대로 둔다 |
| `ix_uploads_uploading_expires` uploads (expires_at) WHERE status = 'UPLOADING' — `ix_uploads_expires_at`을 대체 | `IngestService.sweep_expired` (expires_at을 쓰는 유일한 조회) |
| `ix_uploads_created_at` uploads (created_at) | 감시 규칙 업로드 실패율 |
| `ix_uploads_failed_updated` uploads (updated_at) WHERE error_code IS NOT NULL | 수집 상태 API·정기 점검의 최근 실패 원인 |
| `ix_assets_ingested_at` assets (ingested_at) | 감시 규칙(수집량 급감·격리 급증·용량 예측·회차 무수집), 최근 실패 원인·정기 점검 |
| `ix_assets_not_ready` assets (organization_id, ingest_status, asset_id) WHERE ingest_status <> 'READY_PRIVATE' | 자산 목록 상태 필터(처리 대기·격리·실패)를 커서 순서대로 읽어 limit에서 멈춘다. pg8000은 실행마다 값을 보고 계획을 세우므로 상태가 바인드 매개변수여도 부분 조건에 맞는다 |
| `ix_observations_org_time` observations (organization_id, observed_at) | 관측값 시간축(기관 전체·회차 필터, from·to 필수). 파티션 인덱스라 `ensure_observation_partition`이 만드는 새 월 파티션에도 붙는다 |

버린 대안:
- `(organization_id, ingest_status)`를 `(organization_id, ingest_status, asset_id)`로 바꾸기: 효과는 같지만 asset_id가 유일해 btree 중복 제거가
  안 되어 3.6MB → 50MB가 된다. READY_PRIVATE를 뺀 부분 인덱스는 0.9MB이고 기존 인덱스는 그대로 둔다.
- 보존 만료 검사(`retention.dry_run`·`execute_expired`·`notify_expiring`): 하루 한 번(+ 운영자 dry-run)이고 지금 규모에서 0.1~0.4초 병렬 순차 탐색이다.
  `(retention_until) WHERE deleted_at IS NULL`이면 만료 조회가 1.7ms가 되지만(만료 예고는 기준이 정책 행에 달려 있어 여전히 순차 탐색),
  모든 자산 삽입에 붙는 비용에 비해 이득이 작아 넣지 않았다. 자산이 수백만 건이 되거나 dry-run을 자주 부르면 다시 본다.
- ingested_at에 BRIN: 작지만 자산 행은 처리 단계마다 갱신되어 물리 위치와 시각이 어긋나고 범위가 넓어진다. btree 11MB로 충분하다.
- 이미 괜찮은 경로는 그대로 뒀다: 웹훅 보낼 것(`ix_webhook_deliveries_due`, 0.06ms), 계층 이동 후보(`ix_assets_tier_age`, 0.1~0.3ms),
  계층 유예 삭제, 감사 로그·이벤트·회차·자산 기본 목록(기본키 순서, 0.05~1ms), 장비별 관측값·구간 집계(0.6~1.2ms),
  데이터셋 목록(작은 표 — 비용은 항목별 반복 조회).
  새 ingested_at 인덱스가 생긴 뒤 계층 이동 후보는 모두 HOT인 지금은 그 인덱스를 쓰지만(0.13ms), 오래된 원본을 WARM으로 옮긴 상태를
  흉내 내면(약 10.6만 건, VACUUM 뒤) 다시 `ix_assets_tier_age`를 고른다(0.23ms).
- 인덱스로 못 고치는 것 (질의를 바꿔야 한다 — API는 그대로 두기로 해서 이번에는 하지 않았다):
  자산 목록 촬영 기간 필터(captured_from·to) 300~430ms와 이벤트 from·to 42~45ms. ID(ULID)가 시각과 함께 커져서, LIMIT가 있으면 플래너는
  기본키 순서로 읽어도 금방 찰 것으로 보지만 맞는 행은 끝에 몰려 있다(행 수 추정은 맞다). `(organization_id, capture_start_at)` 인덱스는 이미 있다.
  운영자 전 기관 격리 목록 32~36ms는 기관 조건이 없어 이번 인덱스로 안 되며 운영 화면이라 두었다.
  대기 40,160건일 때 대기 수 세기(`depth_by_type` 15ms, 처리 대기 규칙 18ms)는 행을 다 세야 해 그대로다.

- 계획이 바뀌지 않은 다른 경로는 버퍼 수가 같고, 시간 차이는 측정 흔들림 안이다.
- 크기(이 데이터): 작업 부분 인덱스 1.6MB(대기 4만 건일 때, 평시엔 수십 KB), 업로드 16KB·6MB·200KB, 자산 ingested_at 11MB·not_ready 0.9MB,
  관측값 14MB(센서가 같은 시각에 재서 btree 중복 제거로 작다 — 시각이 제각각이면 행당 약 50바이트, 이 데이터로 약 85MB).
  대체한 uploads expires_at 5.8MB는 없어졌다.
- 쓰기 비용(인덱스 있음 / 없음, 같은 문장을 되돌리는 트랜잭션에서 두세 번씩): 관측값 12만 건 삽입 1.1·2.3초 / 2.3·1.9초,
  업로드 2만 건 생성→완료 1.4·1.9초 / 1.4·1.5초는 공유 호스트의 실행 간 흔들림 안이다. 자산 2만 건 삽입 2.5·2.6·2.7초 / 2.3·2.3·2.7초,
  작업 2만 건 등록→실행→완료 1.7·2.4초 / 1.5·1.8초는 조금 늘었다(행마다 인덱스 항목 하나 — 작업당 약 0.03ms).
  업로드는 status·updated_at이 이제 인덱스 열이라 그 갱신(업로드당 1~2번)은 HOT가 아니다.
- 마이그레이션 시간: 이 데이터에서 upgrade 3.2~3.7초, downgrade 1.1초(파이썬 기동 포함). 보통 `CREATE INDEX`라 만드는 동안 그 표의 쓰기가
  막힌다(인덱스당 0.05~1.8초). 훨씬 큰 운영 표라면 점검 시간에 돌린다.
- 시험: `tests/integration/test_hot_path_indexes.py` — 앱이 보내는 SQL을 잡아 순차 탐색을 끄고 EXPLAIN 해 각 인덱스를 (정렬 없이) 쓰는지,
  결과·순서가 그대로인지 본다. 0024 본문을 비우면 6건 모두 실패하는 것을 확인했다.
- 되돌리기: 0024 down이 새 인덱스를 지우고 uploads(expires_at)를 다시 만든다(자료 변경 없음).
- 후속 제안(이번에 하지 않음, 확인 필요):
  - `ix_observations_series`(organization_id, source_system_id, metric, observed_at)는 `uq_observations_key`의 앞 네 열과 같아 중복이다.
    지우면 관측값 쓰기마다 인덱스 하나가 줄어든다.
  - 끝난 작업(jobs)을 지우는 정책이 없어 업로드 파일당 약 3행씩 계속 쌓인다(가정한 10개월에 109만 행). 보존 기간은 사람이 정할 일이다.
