# ADR-0058: 무결성 검증은 끊겨도 이어서 끝나고, 잠금 순서는 무결성 로그 → 쿼터 행이다

- 상태: accepted
- 날짜: 2026-11-12
- 관련: 04번 요구사항 4.2·4.4·4.6, ADR-0033(클립 잠금 순서), ADR-0044~0046, domain.md 5장(ingest_status), 지시서 12번 클립·업로드 검토 F2·F3

## 맥락

무결성 검증(`IntegrityVerifier.verify`)은 두 트랜잭션이다: ① `RECEIVED → VALIDATING`을 확정 ② 객체를 다시 읽어 해시를 대조하고 등록·정산한다. ①이 확정된 뒤 워커가 죽거나(임대 만료 → 작업이
대기열로 돌아온다) 스트림 오류가 나면, 다시 실행된 검증이 "VALIDATING이라 이미 처리됨"으로 조용히 끝났다. 작업은 DONE인데 자산은 VALIDATING에 영구히 남았고, 업로드 예약(`reserved_bytes`)이
풀리지 않아 쿼터가 영구히 줄었으며, 삭제는 409(ADR-0046이 검증 중 삭제를 거부한다), 재처리도 409였다. 복구 경로가 DB 직접 조작뿐이었다.

또 재검증(격리 → 정식 위치)은 쿼터 행을 먼저 잡고 무결성 로그 잠금을 나중에 잡아, 다른 파생 작업(`record_derived`: 무결성 로그 → 쿼터 행)과 순서가 반대였다. 교착이 나면 피해자는 객체를 이미 옮긴
(저장소 이동은 DB 트랜잭션 안에서 먼저 일어난다) 채 DB만 되돌아가, 기록된 위치에 객체가 없었다. 배경 쓰기 3개와 재검증 12회에서 1회 교착이 재현됐다.

## 결정

1. **VALIDATING(격리 아님)에서도 검증을 이어서 한다.** 첫 트랜잭션은 `RECEIVED` 또는 격리 재검증 또는 중단된 `VALIDATING`이면 진행한다. 검증은 객체를 다시 읽는 일이고 등록·정산은 두 번째 트랜잭션 한 번이라 되풀이해도 안전하다.
2. **두 번째 트랜잭션은 자산 행을 잠근 뒤 `VALIDATING`인지 다시 본다.** 아니면 다른 실행이 먼저 등록·격리한 것이므로 그 상태를 돌려주고 물러난다 — 임대 만료로 작업이 겹쳐 돌아도 등록·무결성 로그·쿼터 정산은 한 번이다.
3. **재검증의 쿼터 이동은 `append_integrity` 뒤로.** 잠금 순서가 모든 경로에서 무결성 로그 → 쿼터 행이다.

## 결과

좋아지는 점: 워커 재시작·일시적 스트림 오류 뒤에도 작업 재시도가 등록을 끝낸다. 예약이 풀린다. 재검증이 파생 작업과 교착하지 않는다.

감수할 점·남은 일(범위 밖, `docs/review-2026-11-12/README.md`):
- **악성코드 검사기가 없는 기간이 길면(`malware_scan_required`인 기관, 5회 시도 약 4분) 작업이 FAILED로 끝나고 자산은 `RECEIVED`에 남는다.** `RECEIVED`에서 `FAILED`로 가는 전이는 domain.md 5장 표에 없어
  상태표 변경이라 **사람의 승인 없이 바꾸지 않는다(AGENTS.md 4)**. 제안: 운영자가 검증 작업을 다시 넣는 경로를 두거나 `RECEIVED → FAILED(예약 해제)` 전이를 표에 추가한다.
- 재검증이 객체를 옮기는 일(`tiers.relocate`)은 여전히 DB 트랜잭션 커밋 전에 일어난다. 잠금 순서 때문에 지는 경우는 없어졌지만 다른 원인으로 롤백되면 기록된 위치에 객체가 없을 수 있다.
- 업로드 취소·만료 정리의 저장소 오류 삼킴(미완성 멀티파트가 남음)은 따로다.

되돌리는 방법: 첫 트랜잭션의 `resume` 조건과 두 번째 트랜잭션의 상태 확인을 지우고 쿼터 이동을 원래 자리로 옮긴다. 마이그레이션·계약 변경 없음.

시험: `tests/integration/test_verify_resume.py` 4개 — 워커가 해시 중 죽은 뒤 임대 만료로 복구, 스트림 오류 뒤 재시도, 겹친 실행이 한 번만 등록·정산, 재검증이 쿼터 행을 쥐기 전에 무결성 로그를 잡음(다른 연결의 NOWAIT로 확인).
수정 전 코드에서 4개 모두 실패하는 것을 확인했다.
