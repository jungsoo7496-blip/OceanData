# ADR-0089: 비식별 검수 목록의 커서 페이지

- 상태: accepted
- 날짜: 2026-11-20
- 관련: 14번 요구사항 4.5(검수자는 배정된 대상만), api-conventions.md 목록 규칙, ADR-0062(요청 DB 차례), ADR-0072(데이터셋 목록 페이지),
  ADR-0077(클립 목록 페이지), 통합 검토 ASSETS-5

## 맥락

`GET /v1/deid-reviews`에는 limit도 커서도 없었다. 검수자는 자기에게 배정된 검수만 받지만, 운영자는 모든 기관의 검수를 처음부터 끝까지
한 응답으로 받았다. 처리기는 행마다 `db.get(Asset, ...)`로 비식별본을 따로 읽었다. 그래서 응답 크기와 질의 수가 플랫폼 이력에 비례해
끝없이 늘고, 그동안 요청 DB 차례(ADR-0062)를 쥐었다. 계약 listDeidReviews에는 `status`만 있었고, api-conventions.md는 목록을
`?limit=&cursor=` → `{items, next_cursor}`, limit 기본 50·최대 500으로 정한다. 같은 묶음의 S03(데이터셋)·S29(클립)가 같은 종류의 빈틈을
고쳤다. 포털의 검수 대기 화면(`web/src/pages/Review.tsx`)은 `status=ASSIGNED` 한 번만 부르고 다음 페이지를 따라가지 않는다.

## 결정

1. **계약 먼저**: listDeidReviews에 공통 매개변수 `cursor`·`limit`(1~500, 기본 50)을 더하고, 200 응답에 `next_cursor`(문자열 또는 null,
   필수)를 더한다. 형식이 틀렸거나 볼 수 없는 검수를 가리키는 cursor, 범위 밖 limit은 400 `VALIDATION_ERROR`(`/query/cursor`·`/query/limit`).
2. **순서는 지금과 같다**: 만든 시각(`created_at`), 같으면 검수 ID 순. 다음 페이지는 `(created_at, review_id) > (커서 검수의 값)`인 행이다(키셋).
   같은 시각의 검수가 페이지 경계에 걸려도 빠지거나 겹치지 않는다.
3. **커서는 그 페이지 마지막 검수의 ID**(base64url)다. 서버가 그 검수의 만든 시각을 한 번 읽어 키셋을 만든다. 읽을 때 목록과 같은 볼 수 있는
   범위(검수자는 자기 검수만)를 걸고, 상태 조건은 걸지 않는다 — `status=ASSIGNED`로 넘기는 사이 마지막 검수가 결정돼 PASSED가 돼도 이어진다.
   형식이 틀렸거나, 없거나, 볼 수 없는 검수면 모두 같은 400이다(다른 검수자의 검수가 있는지 알려 주지 않는다). 검수 행은 지우지 않으므로
   앞 페이지가 준 커서는 계속 쓸 수 있다.
4. **기본 페이지 크기는 규칙대로 50**이다. 포털의 검수 대기 화면은 `limit=500`을 붙여 부른다 — 회차·장비 목록 화면과 같은 방식이다.
5. 페이지의 비식별본은 `asset_id IN (...)` 한 문으로 읽는다. 응답 항목의 모양은 바꾸지 않는다.

버린 대안:
- 커서에 `[만든 시각, 검수 ID]`를 담기(ADR-0077 방식) — 서버가 시각을 다시 읽지 않아도 되지만, 시각 문자열을 해석·검사하는 길(ADR-0077의 범위 밖
  시각이 DB 드라이버에서 500을 낸 문제)을 하나 더 둔다. 검수 ID 하나는 기본 키로 한 번 읽으면 된다.
- 검수 ID 순으로만 넘기기(`paginate()`) — 커서는 단순하지만 지금의 만든 시각 순서가 바뀐다. 검수 ID(ULID)의 시각은 프로세스 시계의
  밀리초이고 같은 밀리초 안에서는 무작위이며, `created_at`은 주입된 시계(`c.clock`)라 순서가 같다는 보장이 없다.
- 기본 크기를 크게(예: 500) 두기 — limit 없이 부르던 클라이언트가 덜 잘리지만 규칙과 다르고, 이 목록에는 ADR-0077처럼 지켜야 할 옛 상한이 없다.
- 계약은 두고 서버에서만 잘라 주기 — 잘렸는지 알 길이 없어 S03·S29가 고친 '말없이 잘림'이 된다.

## 결과

좋아지는 점: 운영자의 검수 목록이 한 번에 최대 500건이고 질의 수가 페이지 크기와 상관없이 일정하다. 잘렸는지는 `next_cursor`로 안다.
응답은 필드 하나가 늘었을 뿐 기존 필드는 같다.

감수할 점:
- limit 없이 부르던 클라이언트는 처음 50건만 받는다. 저장소 안의 호출자는 포털 한 곳이고 `limit=500`으로 바꿨다. 다른 클라이언트가 있으면
  `next_cursor`를 따라가야 한다.
- 포털의 검수 대기 화면은 배정 대기가 500건을 넘으면 첫 500건만 보여 준다 — 더 보기는 따로 한다.
- `deid_reviews`에는 `(created_at, review_id)` 색인이 없다. 검수자 조건은 `reviewer_id` 색인을 쓰고, 운영자 목록은 거른 행을 정렬한 뒤 limit만큼 읽는다.
  검수가 아주 많아지면 색인(마이그레이션)을 다시 본다.
- 페이지를 넘기는 사이 새 검수가 생기면 만든 시각 순으로 뒤에 붙으므로 마지막 페이지에서 보인다.
- 계약이 바뀌어 웹·에이전트 생성 타입을 다시 만들어야 한다.

되돌리는 방법: 계약 listDeidReviews의 `cursor`·`limit`·`next_cursor`·설명을 지우고, `list_reviews`의 페이지 처리와 `_review_cursor`,
포털의 `limit=500`을 되돌린 뒤 웹·Go 타입을 다시 만든다. 마이그레이션 없음.

시험: `tests/integration/test_deid_review_list_pages.py` 8개 — 운영자 목록을 `limit=2`로 끝까지 넘기면 만든 시각·ID 순(같은 시각 둘 포함)과 같고 세 쪽,
51건이면 조건 없이 50건과 `next_cursor`, 다음 쪽 1건과 null. 검수자는 자기 검수만 받고 `status=ASSIGNED`로 넘겨도 이어지며, 다른 검수자의 검수 ID로
만든 커서는 400. `limit` 0·501, 검수 ID가 아닌 커서, 없는 검수의 커서는 400. 검수 20건 쪽과 2건 쪽의 질의 수 차이가 1 이하. 모든 응답을 계약과 대조한다.
수정 전 코드에서 8개 모두 실패하는 것을 확인했다(limit을 무시하고 전부 줌, `next_cursor` 없음, 잘못된 limit·커서가 200, 검수 20건 쪽이 18문 더 많음).
