# ADR-0054: 에이전트의 Idempotency-Key는 요청 본문에서 만든다

- 상태: accepted
- 날짜: 2026-11-12
- 관련: 06번 요구사항 5.4, 06번 design.md(멱등 키), `contracts/schemas/upload-manifest.schema.json`(`client.local_collection_id`), domain.md 7장, 지시서 12번 E2E 발견 F1

## 맥락

서버는 같은 `Idempotency-Key`로 **다른 본문**이 오면 409 `IDEMPOTENCY_CONFLICT`로 거부한다(`services/idempotency.py`가 본문 해시를 비교).
에이전트는 업로드 등록 요청의 키(= `client.local_collection_id`, 계약: "에이전트가 파일마다 만든 로컬 ID. Idempotency-Key로도 쓴다")를
`sha256(원천 장비|파일 해시|variant|회차 표시값|규칙)`의 앞 32자로 만들었다. 이 입력에는 파일 이름과 상대 경로가 없지만 본문에는
`file.original_filename`·`file.original_relative_path`가 들어간다.

그래서 실제 에이전트와 로컬 스택을 이은 E2E(지시서 12번)에서 이 일이 났다. `clip_small.mp4`를 올린 뒤 같은 바이트를 `cam01/clip_dup.mp4`로 복사하자
24시간 안에는 키가 같고 본문이 달라 409가 났고, 에이전트는 `IDEMPOTENCY_CONFLICT`를 재시도 없는 거부로 보고 그 파일을 FAILED로 두었다
(`status`: "실패 1개 / 최근 오류 IDEMPOTENCY_CONFLICT"). 같은 내용이라 서버가 `ALREADY_REGISTERED`로 답했을 요청이 키 때문에 거기까지 가지도 못했다.

같은 종류의 어긋남이 본문의 다른 필드에도 있었다: `client.version`(자동 갱신으로 버전이 바뀐 뒤 응답을 못 받은 등록을 다시 보낼 때),
규칙의 `data_role` 기본값(정책이 바뀐 뒤), `byte_size`. 이름만 고쳐서는 이 분류 전체가 닫히지 않는다.

## 결정

키를 **본문의 함수**로 만든다. `manifest()`가 `client.local_collection_id`를 뺀 본문을 정본 JSON(Go `map`은 키 순서로 직렬화)으로 만들어
sha256의 앞 32자를 `lc-` 뒤에 붙이고, 같은 값을 `client.local_collection_id`와 `Idempotency-Key`에 쓴다. 계약 문구("파일마다 만든 로컬 ID,
Idempotency-Key로도 쓴다")는 그대로 맞고 계약 파일은 바뀌지 않는다.

- 본문이 같으면 키가 같다: 응답을 못 받은 등록의 재시도는 서버에서 처음 응답을 되받는다(기존 성질 유지).
- 본문이 하나라도 다르면 키가 다르다: 같은 내용의 복사본·옮긴 파일·버전/정책이 바뀐 뒤의 재시도는 새 요청이 된다.
  서버는 `(기관, 원천 장비, 체크섬)`으로 중복을 판정하므로(`create_upload`) 이 요청은 `ALREADY_REGISTERED`(영수증 확인 뒤 완료) 또는
  진행 중 세션 재사용(201)으로 끝난다. 중복 자산이나 중복 저장은 생기지 않는다.
- 본문에 새 필드가 생겨도 키가 자동으로 따라간다(키 입력 목록을 따로 관리하지 않는다).

버린 대안:
- *키 입력에 파일 상대 경로만 더하기*: F1은 닫지만 버전·정책 변경 같은 같은 계열의 틈이 남고, 본문에 필드가 늘 때마다 키 입력을 따로 맞춰야 한다.
- *`IDEMPOTENCY_CONFLICT`를 받으면 키 없이 다시 보내기*: 서버가 거부한 이유를 숨긴다. 키가 본문과 맞는 것이 원인 해결이다.
- *서버가 같은 키·다른 본문을 허용하기*: 계약(409)과 다른 클라이언트의 안전장치를 없앤다.

## 결과

좋아지는 점: 에이전트 자신의 요청이 서버의 멱등 검사에 걸려 영구 실패하지 않는다. 같은 내용의 파일을 여러 이름으로 두는 현장 습관(복사본,
이름 변경)이 안전하다. 시험 `TestIdempotencyKeyFollowsTheRequestBody`가 "키가 같다 ⇔ 본문이 같다"를 쌍마다 확인해 같은 종류의 퇴행을 막는다.

감수할 점:
- `local_collection_id`가 에이전트 버전·정책에 따라 달라질 수 있다. 서버는 이 값을 `ingest_context`에 저장만 하고 조회·연결에 쓰지 않는다
  (`ingest.py`, 이 저장소의 다른 소비자 없음). 같은 파일은 체크섬으로 한 자산만 만들어지므로 저장되는 값은 처음 등록 때의 것 하나다.
- 업그레이드한 에이전트의 첫 재시도는 옛 키와 다른 키를 쓴다. 서버가 체크섬으로 같은 세션을 돌려주므로 영향이 없다.
- 같은 내용의 두 파일이 동시에 올라가면(처음 것이 진행 중) 두 번째도 같은 업로드 세션을 받아 같은 파트를 다시 보낼 수 있다. 완료는 한 번만
  되고 나머지는 이미 완료된 세션(409)으로 `awaitReceipt` 경로를 탄다(`resume`). 이전에는 두 번째 파일이 FAILED로 끝나 이 경로에 오지 않았다.

되돌리는 방법: `manifest()`의 키 계산을 이전 식으로 되돌린다(계약·서버 변경 없음). 단 F1이 다시 생긴다.

시험: `agent/internal/core/idempotency_key_test.go` — 같은 내용·다른 이름이 모의 서버(실제 서버처럼 같은 키·다른 본문을 409로 거부)에서 완료로
끝나는지, 본문이 다른 8가지 경우(이름·폴더·해시·크기·회차·규칙·정책 역할·버전)에서 키가 다른지. 수정 전 코드에서 두 시험 모두 실패하는 것을 확인했다.
