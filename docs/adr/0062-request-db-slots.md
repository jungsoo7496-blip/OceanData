# ADR-0062: 요청은 DB 작업 차례를 비동기로 받은 뒤 연결을 쓴다

- 상태: accepted
- 날짜: 2026-11-12
- 관련: 01번 요구사항 4(오류 응답)·8(지표), ADR-0053(요청 커밋을 응답 앞으로·같은 멱등 키 대기), 지시서 12번 커밋 시점 검토 K1·K8, api-conventions.md 오류 코드 표

## 맥락

모든 경로는 DB 세션을 `deps.DB`(function 범위 `get_db`)로 받는다. 지금까지 `get_db`·`get_principal`·`require`와 경로 함수는 모두 동기 함수라 FastAPI가 요청마다 스레드 풀(anyio 기본 40)을
여러 번 오가며 돌렸다(인증 → 권한 → 경로 → 커밋). 요청은 첫 조회 때 연결을 꺼내 커밋할 때까지 쥐는데, 그 사이 다음 스레드 차례를 기다린다.
동시 요청이 스레드 한도를 넘으면 스레드는 연결을 기다리는 요청들이 차지하고, 연결은 다음 스레드 차례를 기다리는 요청들이 쥐어 **서로를 기다렸다** — 연결 대기 시간(`pool_timeout` 30초)이 지나 500이 났다.

검토(K8)는 "풀을 스레드 한도에 맞추기"를 방향으로 적었지만 재현해 보니 풀 크기로는 풀리지 않는다. `GET /v1/me` 150건 동시 요청에서 풀 2개는 120건, **풀 60개(스레드 한도보다 크다)도 62건이 500**이었다.
요청 수가 스레드 + 연결보다 많으면 어느 크기든 같은 순환이 생긴다.

## 결정

1. **`get_db`를 비동기 의존성으로 바꾸고, 세션을 만들기 전에 DB 작업 차례(`RequestSlots`)를 이벤트 루프에서 기다린다.** 기다리는 요청은 스레드도 연결도 쥐지 않는다.
   차례를 받은 요청만 연결과 스레드를 쓰므로, 차례 수를 연결 풀과 스레드 한도보다 작게 두면 차례를 받은 요청은 반드시 연결과 스레드를 얻는다 — 순환 대기가 없다.
2. 커밋·되돌리기·닫기는 그대로 스레드 풀에서 돌린다(이벤트 루프를 막지 않는다). 요청이 취소돼도 되돌리기·닫기는 끝까지 한다(`CancelScope(shield=True)`).
   커밋이 응답보다 먼저라는 ADR-0053의 순서와 커밋 충돌의 409 매핑은 바뀌지 않는다.
3. **차례 수 기본값은 `(DB_POOL_SIZE + DB_MAX_OVERFLOW) // 2`**(기본 10 + 20 → 15). 요청 하나가 자기 세션과 감사 기록·작업 등록의 별도 연결을 함께 쥘 수 있어서다.
   어떤 값을 주든 스레드 한도 − 1을 넘지 않게 줄인다. `DB_REQUEST_SLOTS`로 정할 수 있다.
4. **차례를 `DB_REQUEST_SLOT_WAIT_S`(기본 10초) 안에 받지 못하면 503 `SERVICE_UNAVAILABLE` + `Retry-After: 1`**이다(전에는 30초 뒤 500 `INTERNAL`). 과부하는 어느 작업에서나 날 수 있어
   계약 머리말과 api-conventions.md 오류 표에 적었다. 지표 `db_request_slot_timeouts_total`을 센다.
5. 연결 풀 크기·대기 시간을 설정으로 뺀다: `DB_POOL_SIZE`(10)·`DB_MAX_OVERFLOW`(20)·`DB_POOL_TIMEOUT_S`(30). `.env.example`·Compose에 넣었다(빠뜨리면 배포에서 켤 수 없다 — W6).
   이때 `.env.example`·Compose가 선택 숫자를 빈 값으로 두면(`STORAGE_CAPACITY_BYTES=`) 기동이 실패하던 기존 문제도 고쳤다 — 빈 값은 '설정 안 함'이다.

버린 대안: 풀을 스레드 한도보다 크게 — 위 재현대로 풀리지 않는다. 스레드 한도를 크게 — 같은 순환이 더 큰 수에서 생기고 스레드 비용만 는다.
요청마다 모든 동기 단계를 한 스레드에서 돌리기 — FastAPI가 의존성마다 따로 스레드에 보내는 구조라 경로 151곳을 바꿔야 한다. uvicorn `--limit-concurrency` — DB를 쓰지 않는 요청까지 막고 503 형식이 계약(problem+json)과 다르다.

## 결과

좋아지는 점: 동시 요청이 스레드 한도를 넘어도 500이 나지 않고 차례대로 처리된다(풀 2개·요청 150건이 6초 안에 모두 200). 과부하가 길면 500이 아니라 재시도해도 되는 503이다. 풀 크기를 배포에서 정할 수 있다.

감수할 점:
- 한 프로세스에서 동시에 DB 작업을 하는 요청이 기본 15개로 묶인다(전에는 이론상 30개 연결까지 썼지만 폭주에서는 막혔다). 처리량이 부족하면 풀과 차례를 함께 늘리되,
  **프로세스 수 × (풀 + 초과)가 PostgreSQL `max_connections`보다 작아야 한다**(워커도 같은 설정의 풀을 쓴다).
- 같은 멱등 키 대기자(ADR-0053, 프로세스당 8개·2초)는 차례를 쥔 채 기다린다 — 키 단위 대기 상한이 그대로 막는다.
- 요청 안에서 세 개 이상 연결을 동시에 쥐는 경로가 생기면 기본 차례 수(÷2)로는 모자랄 수 있다. 그럴 때는 `DB_REQUEST_SLOTS`를 줄인다.
- 차례 표는 이벤트 루프마다 따로 둔다(uvicorn은 루프 하나, 시험은 여럿).

되돌리는 방법: `get_db`를 동기 생성기로 되돌리고(`c.db_slots.hold()` 제거) `app/db/slots.py`를 지운다. 설정·Compose 줄은 남겨도 해가 없다. 마이그레이션 없음. 계약은 머리말 설명 한 줄.

시험: `tests/integration/test_request_burst.py` — 설정으로 풀을 2개로 줄인 앱을 실제 uvicorn으로 띄우고 원시 소켓으로 `GET /v1/me` 150건을 동시에 보내 모두 200인지 본다.
수정 전 코드에서는 응답을 60초 안에 받지 못한 요청이 생겨 실패하는 것을 확인했다. `tests/unit/test_request_slots.py` — 차례 한도·대기 시간 초과 503·스레드 한도보다 작음·빈 설정 값·기본 차례 수.
