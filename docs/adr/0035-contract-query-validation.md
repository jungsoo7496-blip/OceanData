# ADR-0035: 조회 조건은 계약 스키마로 검사하고, 저장할 수 없는 문자와 처리 못 한 예외를 문제 응답으로 맞춘다

- 상태: accepted
- 날짜: 2026-11-05
- 관련: 04번 요구사항 10.2(Schemathesis)·작업 20, 01번 요구사항 4(요청 ID)·10.2(오류 형식), `contracts/openapi.yaml`

## 맥락
Schemathesis 계약 시험(04번 작업 20)이 처음 돌았을 때 계약과 서버가 다른 곳 8건(M1~M8)을 찾았다.
- 계약 쪽: 목록의 잘못된 limit·cursor 400(M1), 완료된 업로드 파트 조회 409(M2), 범위 밖 장비 404(M5), 모든 인증 작업의 호출 제한
  429(M6), 완료 요청 상한(M7)이 계약에 없었다.
- 서버 쪽: 문제 응답 instance가 디코딩한 경로라 URI 참조가 아니었고(M3), 목록 조회가 계약을 어긴 조건(열거값·ID 형식·UTC 'Z'·길이)을
  200 빈 목록으로 받았으며(M4), 경로·조회·본문 문자열의 NUL이 PostgreSQL까지 가서 500이 났다(M8). 그 500 응답은 request_id가
  빈 문자열이었다 — Starlette의 일반 예외 처리기는 가장 바깥 미들웨어에서 돌아 요청 ID 문맥이 이미 풀린 뒤였다.

## 결정
1. **계약 보강**: 인증 작업 141개 모두에 429(TooManyRequests), 조회 조건이나 본문이 있는 작업에 400, listUploadParts에 409,
   createUpload에 404, CompleteRequest에 서버와 같은 상한(parts ≤ 10000, part_number ≤ 10000, etag ≤ 200자).
   계약 검사기(`tools/validate_contracts.py`)는 openapi.yaml의 중복 키를 오류로 본다(PyYAML은 조용히 덮어써 웹 타입 생성만 실패했다).
2. **조회 조건 = 계약 스키마**(`app/api/contract_query.py`): 시작할 때 openapi.yaml에서 작업별 문자열 조회 매개변수 스키마를 읽어
   검사기를 만든다. 인증·호출 제한 뒤(`get_principal` 끝)에 받은 그대로의 문자열을 검사하고 어기면 400 VALIDATION_ERROR
   (`/query/<이름>`). 숫자·불리언은 FastAPI 형 변환이 이미 본다. 계약에 없는 조건은 건드리지 않는다.
   버린 대안: 엔드포인트마다 Pydantic 형·정규식을 손으로 옮기기 — 19개 작업의 열거값·형식이 계약과 따로 놀게 된다.
3. **NUL**: 경로 값에 NUL이 있으면 그런 자원은 없으므로 404. 조회 조건·본문 문자열의 NUL 등 PostgreSQL이 저장할 수 없는 문자
   (SQLSTATE 22021·22P05)는 DB 오류 처리기에서 400 `invalid_character`로 바꾼다. 다른 DB 오류는 그대로 500.
4. **처리 못 한 예외**: 요청 문맥 미들웨어가 직접 잡아 요청 ID(본문·`X-Request-Id` 헤더 같음)와 instance를 단 500 문제 응답을
   보낸다. 스택·SQL은 로그에만 남는다(기존 규칙 그대로). instance는 퍼센트 인코딩한 경로다.

## 결과
- 좋아지는 점: Schemathesis 양성·음성 시험을 봐주는 표 없이 돌린다(NUL·비ASCII 경로 생성 포함). 계약과 다른 조건은 조용히
  빈 목록이 아니라 400으로 알려 준다. 500 응답도 요청 ID로 로그를 찾을 수 있다.
- 감수할 점: 그동안 계약을 어긴 조회 조건(예: `+09:00` 시각)을 보내던 클라이언트는 400을 받는다(웹·에이전트·예제는 계약 형식만
  쓴다). 매 인증 요청마다 문자열 조건 몇 개를 jsonschema로 검사하는 비용이 든다.
- 되돌리는 방법: `get_principal`의 호출 한 줄과 DB 오류 처리기를 지우면 이전 동작. 계약 보강은 그대로 두는 것이 맞다.
