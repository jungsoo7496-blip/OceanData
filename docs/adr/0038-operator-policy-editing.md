# ADR-0038: 운영 콘솔 정책 편집 — 쿼터·보존·작업 우선순위, 다중 인증·사유·전후 감사, 바꿀 수 없는 만료 동작

- 상태: accepted
- 날짜: 2026-11-05
- 관련: 09번 요구사항 10.1·10.2·작업 13, 08번 요구사항 3.1(보존 정책 표), 05번 요구사항 6.1(우선순위), domain.md 9장

## 맥락
운영 콘솔은 기관·사용자·장비·정책(쿼터·보존·샘플링·우선순위)을 관리하고, 정책을 바꾸면 전후 값과 사유를 감사해야 한다.
지금까지 쿼터·보존·작업 정책은 마이그레이션 시드 값이거나 서버 명령(org-policy)으로만 바꿀 수 있었다.

## 결정
1. **범위**: 기관 정책(쿼터·악성코드 검사 요구), 보존 정책 표(대상별 일수·만료 동작·알림), 작업 정책(우선순위·최대 시도)을
   `GET/PATCH /v1/organization-policies`, `/v1/retention-policies`, `/v1/job-policies`로 연다(계약 먼저).
   - 사용자 편집은 구성원 관리(02번 작업 12, Keycloak 관리 API 연동 결정 대기)와 함께 한다.
   - 장비는 기존 장비 API·정책 명령을 쓴다.
   - "샘플링" 정책은 무엇을 가리키는지(무결성 표본 수? C1 미리보기 표본?) 정해지지 않아 확인 필요로 남긴다.
2. **권한**: 조회는 PLATFORM_OPERATOR, 바꾸기는 PLATFORM_OPERATOR + 다중 인증 + 사유(2~500자) 필수.
   바뀐 항목만 `{from, to}`로 감사(ORG_POLICY_CHANGED·RETENTION_POLICY_CHANGED·JOB_POLICY_CHANGED). 바뀐 것이 없으면 감사하지 않는다.
3. **보존 정책 적용 시점**: 새로 등록·파생되는 자산부터. 이미 계산한 retention_until을 다시 계산하지 않는다
   (기간을 줄여 기존 자산이 한꺼번에 만료 대상이 되는 사고를 막는다). 만료 실행은 그때의 만료 동작을 읽으므로 DELETE → KEEP은
   기존 대상도 바로 지킨다. DELETE에는 보존 일수가 있어야 한다.
4. **바꿀 수 없는 만료 동작(409)**: EVIDENCE·DATASET(증빙·데이터셋 사본 — 사람 결정 없이 바꾸지 않음),
   QUARANTINE:UNKNOWN_SESSION·MISSING_REQUIRED_METADATA(손상 없는 원본일 수 있어 자동 삭제하지 않음, domain.md 9장).
   알림 일수는 바꿀 수 있다. 표에 없는 대상은 만들지 않는다(404).
5. **쿼터**: 사용량보다 낮출 수 있다(새 업로드만 막히고 데이터는 지우지 않음) — 응답의 over_quota로 알린다.
6. **작업 우선순위**: 정책과 함께 대기 중(QUEUED) 작업의 우선순위도 바꾼다(작업 행이 등록 때 우선순위를 복사하므로).
   최대 시도는 새로 등록하는 작업부터.

## 결과
- 좋아지는 점: 운영자가 서버 명령 없이 화면에서 정책을 바꾸고, 누가 왜 무엇을 바꿨는지 감사 로그로 남는다.
- 감수할 점: 보존 기간을 늘려도 기존 자산의 기한은 그대로다(필요하면 별도 재계산 명령 — 결정 필요).
- 되돌리는 방법: 라우터·권한을 지우면 이전처럼 시드·명령으로만 바꾼다. 스키마 변경·마이그레이션 없음.
