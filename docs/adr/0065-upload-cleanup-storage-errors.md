# ADR-0065: 업로드 취소·만료 정리는 저장소 정리를 확인한 뒤에만 세션을 끝낸다

- 상태: accepted
- 날짜: 2026-11-12
- 관련: 04번 요구사항 3.3·3.4(만료·취소 정리), 1.5(예약), ADR-0042(만료 정리 부분 인덱스), ADR-0044(크기 불일치 정리 503), ADR-0045(재신고 정리 503), ADR-0046(삭제 중 업로드·완료 객체 409), ADR-0053(완료 재시도), ADR-0055(지웠다고 확인된 객체), ADR-0059(세션별 트랜잭션), ADR-0084(중단 뒤 다시 확인 — 아래 갱신), 지시서 12번 클립·업로드 검토 C4

## 맥락

업로드 세션을 끝내는 정리(`IngestService._release`)는 여러 곳에서 부른다: 만료 정리기(`sweep_expired`, 워커가 5분마다), 요청 중 만료(`GET .../parts`·`POST .../complete`), 사용자 취소(`DELETE /v1/uploads/{id}`),
만료 세션 재신고(`POST /v1/uploads`), 완료 때 크기 불일치, 자산·회차 삭제(`preserve_asset`).
뒤의 세 곳은 저장소 정리에 실패하면 503이었지만(ADR-0044·0045·0046), 앞의 세 곳은 `abort_multipart_upload` 예외를 경고로만 남기고 세션을 EXPIRED·ABORTED로 끝내고 예약을 풀었다.
검토 재현(C4): 저장소 장애 중에 만료 정리가 돌면 세션은 EXPIRED, 예약 0인데 멀티파트와 올라간 파트는 저장소에 그대로 남았고, 세션이 끝났으므로 다시 정리하지 않았다. 사용자 취소도 204였다.

두 번째 빈틈: 완료 요청은 저장소에서 멀티파트를 완료한 뒤 DB를 확정한다(ADR-0053). 그 사이에 프로세스가 죽으면 DB는 UPLOADING이고 저장소에는 완성 객체가 있다.
클라이언트가 유효 기간 안에 완료를 다시 보내면 이어서 끝나지만(ADR-0053), 다시 오지 않으면 만료 정리가 멀티파트 중단(이미 완료돼 NoSuchUpload이거나 성공)만 하고 자산 기록을 지웠다.
객체는 어느 자산도 가리키지 않고 쿼터에도 세지 않은 채 남았다(검토 재현 `test_completed_object_orphaned_by_sweeper`). 취소·재신고도 같았다.

## 결정

1. **저장소 실패를 둘로 나눈다.** 멀티파트 중단의 `NoSuchUpload`(이미 중단·완료된 멀티파트)는 정리된 것으로 본다 — S3 어댑터가 이미 성공으로 돌려주던 것을 포트의 약속으로 적었다.
   그 밖의 실패(시간 초과, `SlowDown` 같은 다른 S3 오류)는 `UploadCleanupFailed`(503 `STORAGE_UNAVAILABLE`, `Retry-After: 30`)로 올리고 세션을 끝내지 않는다. 모든 호출 경로가 같은 규칙이다(`require_cleanup` 인자는 없앴다).
   - 만료 정리기: 그 세션의 트랜잭션을 되돌려 UPLOADING·예약·자산 기록을 그대로 두고, 업로드 ID와 저장소 예외 이름으로 오류 로그(`expired_upload_release_failed`)를 남긴 뒤 다음 세션으로 간다. 다음 주기가 다시 시도한다. 저장소 주소·멀티파트 ID는 로그에 남기지 않는다.
   - 사용자 취소·요청 중 만료(`GET .../parts`, `POST .../complete`): 204·410 대신 503과 `Retry-After`. 다시 요청하면 이어서 정리한다.
2. **멀티파트를 중단하기 전에 이 키에 완성 객체가 있는지 `head_object`로 확인한다.** 있으면 멀티파트 중단 뒤 객체를 지우고, 지운 뒤에만 세션을 끝낸다. 삭제 호출이 실패해도 객체가 실제로 없으면 지운 것이고(ADR-0055와 같은 기준),
   남았거나 확인할 수 없으면 1과 같이 세션을 유지한다(요청은 503, 정리기는 다음 주기).
   - 확인을 중단보다 먼저 하는 까닭: 확인이 실패하면 저장소도 그대로여야 어느 경로에서 다시 보내도 같은 정리에 닿는다. 크기 불일치 취소는 완료 요청 안에서 하므로 그 503 뒤에는 완료를 다시 보낸다.
     중단 뒤에 확인하다 실패하면, 다시 보낸 완료는 이미 중단된 멀티파트의 파트 목록을 보게 되어(moto는 `NoSuchUpload`로 503, SeaweedFS 3.80은 빈 목록 — ADR-0046) 이 취소에 다시 닿지 못하고, 세션은 유효 기간(7일)이 끝날 때까지 예약을 쥔 채 남았다(검토 지적).
     완료 요청은 업로드 행 잠금을 쥐고 저장소 완료부터 DB 확정까지 한다(3). 다만 저장소 완료 호출이 시간 초과·연결 오류로 503이 되면(ADR-0082) 잠금이 풀린 뒤에도
     저장소가 그 완료를 마칠 수 있어, 확인과 중단 사이에 완성 객체가 생길 수 있다. 처음 확인에서 객체가 없었으면 중단 뒤에 한 번 더 확인한다(ADR-0084, 아래 갱신).
   - 살아 있는 다른 자산(삭제되지 않았고 바이너리가 있는 자산 — 이 업로드의 UPLOADING 자산은 뺀다)이 같은 키를 가리키면 그 자산의 객체이므로 지우지 않고 세션만 끝낸다. 키에 자산 ID가 들어 있어 정상 흐름에서는 일어나지 않는 방어다.
   - C0 자산에서 연 세션도 같다 — 자산은 바이너리 없는 기록으로 돌아가므로(`asset_was_metadata_only`) 객체를 남기면 고아가 된다.
   - 삭제 경로(`preserve_asset`)는 그대로 409다: 완성 객체가 있으면 지우지 않는다(ADR-0046). 확인이 중단보다 앞서므로 이때는 멀티파트 중단을 부르지 않는다(완성 객체가 있으면 그 멀티파트는 이미 완료돼 중단할 것이 없다).
     그 세션은 이후 완료 재시도로 등록되거나, 만료되면 정리기가 위 규칙으로 정리한다.
3. 잠금 순서와 트랜잭션은 그대로다: 업로드 행 잠금 → 저장소 정리(확인·중단·삭제) → 쿼터 행 잠금·예약 해제 → 확정(ADR-0059). 완료 요청은 저장소 완료부터 DB 확정까지 업로드 행을 쥐므로,
   진행 중인 완료의 객체를 정리가 지우는 일은 없다(`test_completion_serializes_with_upload_cleanup`). 503으로 끝난 완료(ADR-0082)는 잠금을 놓았으므로,
   그 뒤 저장소가 마친 객체는 정리가 다른 완성 객체처럼 다룬다(ADR-0084). 객체가 있을 때만 하는 자산 조회는 잠그지 않는 읽기다.
4. 계약을 먼저 고쳤다: `abortUpload`·`listUploadParts`에 503과 설명을 넣고, `completeUpload` 설명에 만료 정리 실패를 적었다. `listUploadParts`는 전에도 파트 목록 조회 실패 때 503이었는데 계약에 없었다.
5. **저장소 수명주기 규칙(`AbortIncompleteMultipartUpload`)은 설정하지도 가정하지도 않는다.** SeaweedFS가 이 규칙을 지원하는지는 **확인 필요**이고, 쓸지(앱 정리와 함께 둘지)는 사람 결정으로 남긴다(HANDOFF '남은 일' 4절 ④).
   새 표·재시도 목록도 두지 않는다 — 정리하지 못한 세션이 UPLOADING으로 남아 있는 것이 곧 재시도 대상이다(ADR-0042 부분 인덱스로 다시 후보에 오른다).

버린 대안:
- 만료 때 남은 완성 객체를 받아들이기(RECEIVED로 올려 검증) — 유효 기간이 지나 클라이언트가 포기했을 수 있는 파일을 등록하게 되고, 만료는 410과 정리라는 요구사항 3.3과 맞지 않는다. 유효 기간 안의 완료 재시도는 지금처럼 이어서 끝난다(ADR-0053).
- 정리하지 못한 세션을 표시하는 새 열·재시도 목록 — 마이그레이션이 필요하고, 오늘 범위는 앱 쪽의 보수적인 부분만이다.
- 실패를 삼키고 저장소 수명주기 규칙에 맡기기 — 지원 여부를 모른다.
- 정리기가 실패한 세션의 만료 시각을 뒤로 미루기(뒤 후보에 차례를 주려고) — 만료 시각은 클라이언트에 보이는 값이고, 미루면 세션이 다시 유효해진다.
- 완성 객체 확인은 중단 뒤에 두고, 파트 목록 조회의 `NoSuchUpload`를 '멀티파트가 이미 없다'로 보고 정리로 보내기 — 합성 데이터로 띄운 SeaweedFS 3.80은 중단 뒤 파트 목록이 200과 빈 배열이었다(ADR-0046).
  운영 저장소에서는 알아챌 수 없고, 저장소 완료 뒤 죽은 요청의 완성 객체와도 구별해야 한다. 확인을 중단 앞으로 옮기면 저장소와 관계없이 확인 실패로 이 상태가 생기지 않는다.

## 결과

좋아지는 점: 저장소가 정리를 확인해 준 세션만 끝난다. 장애가 지나가면 다음 주기(또는 다시 보낸 요청)가 이어서 정리하므로 미완성 멀티파트와 파트가 저장소에 쌓이지 않는다.
예약도 실제로 정리될 때까지 남아 쿼터와 저장소 사용이 어긋나지 않는다. 죽은 완료 요청이 남긴 완성 객체도 만료·취소·재신고 때 지워진다.

감수할 점:
- 저장소 장애 중에는 취소·요청 중 만료가 204·410 대신 503이다(클라이언트는 `Retry-After` 뒤 다시 보낸다). 에이전트는 5xx를 오프라인으로 보고 다시 시도하며, 409·410 처리는 그대로다.
- 정리마다 HEAD를 한 번 더 부른다(전에는 삭제 경로만). ADR-0084부터는 처음 확인에서 객체가 없으면 중단 뒤에 한 번 더 부른다. 그래서 정리기·취소·요청 중 만료도 HEAD 실패만으로 503·다음 주기 재시도가 된다(이때 저장소는 바꾸지 않는다).
- 멀티파트 중단 호출이 실패했는데 저장소에서는 중단이 끝난 경우(응답 유실)는 남는다. 같은 정리(취소·정리기·요청 중 만료·재신고·삭제)를 다시 하면 중단의 `NoSuchUpload`나 성공으로 이어서 끝나지만,
  크기 불일치 취소 뒤 완료를 다시 보내거나 재개(`GET .../parts`)하면 이미 중단된 멀티파트를 보게 되어(moto는 503, SeaweedFS 3.80은 빈 파트 목록) 유효 기간이 끝나 정리기가 정리할 때까지 세션과 예약이 남는다.
  크기 불일치 취소의 중단 실패는 이 변경 전에도 503이었다(ADR-0044). 이 상태를 알아내려면 저장소별 응답 확인이나 세션 표시(마이그레이션)가 필요해 오늘 범위에서 뺐다.
- 영구적으로 실패하는 세션(버킷이 없어짐·권한 없음 등)은 매 주기 오류 로그를 남기며 UPLOADING·예약으로 남는다. 후보는 만료 시각이 오래된 순으로 100개라, 그런 세션이 100개를 넘으면
  그 뒤의 만료 세션은 정리되지 않는다 — 오류 로그로 드러나며 원인을 고쳐야 풀린다.
- 수정 전에 이미 끝난 세션이 운영 저장소에 남긴 미완성 멀티파트·고아 객체는 이 변경으로 정리되지 않는다. 버킷의 미완성 멀티파트 목록과 DB를 대조하는 일회성 점검이 필요한지는 사람 결정이다.

되돌리는 방법: `IngestService._release`의 저장소 정리 블록을 예전 형태(실패는 경고만, 재신고·크기 불일치·삭제 경로만 503)로 되돌리고 `_remove_completed_object`·`UploadCleanupFailed`를 지운다.
계약의 설명과 503 줄을 되돌리고 웹·에이전트 타입을 다시 만든다. 마이그레이션 없음.

시험: `tests/integration/test_upload_cleanup_storage_errors.py` 21개(실제 S3 API — moto 또는 TEST_S3_ENDPOINT). 만료 정리기가 멀티파트 중단 실패(시간 초과·`SlowDown`)에서 세션·예약·자산·멀티파트를 남기고
업로드 ID·예외 이름만 담은 오류 로그를 쓴 뒤 다음 주기에 정리(2), `NoSuchUpload`는 정리된 것으로 끝냄(1), 사용자 취소 503 → 다시 보내면 204(2), 요청 중 만료(parts·complete) 503 → 다시 보내면 410(2),
완성 객체 확인(HEAD) 실패 때 정리기·취소가 세션·예약과 멀티파트를 그대로 두고 단계 `head_object`를 기록(2),
죽은 완료가 남긴 완성 객체를 정리기·취소·parts·complete·재신고가 지움(5), 객체 삭제 실패 때 세션 유지와 재시도(2), 삭제 호출이 예외를 냈지만 객체가 없으면 지운 것으로 끝냄(1), 삭제와 그 뒤 확인이 모두 실패하면 세션 유지(1),
C0 자산 세션(1), 살아 있는 다른 자산이 가리키는 객체는 지우지 않음(1), 크기 불일치 취소에서 확인이 실패하면 503·멀티파트 유지 → 완료를 다시 보내면 409로 취소를 마치고 그다음은 410(1).
수정 전 코드에서 19개가 실패하는 것을 확인했다(나머지 2개 — `NoSuchUpload`와 살아 있는 자산의 객체 — 는 수정 전에도 맞던 동작을 지키는 방어 시험이다).
확인을 중단 앞으로 옮긴 것은 검토 지적을 반영한 것이다. 크기 불일치 취소 시험과 HEAD 실패 시험 2개는 옮기기 전 코드(중단 뒤 확인)에서도 실패하는 것을 확인했다(503 뒤 멀티파트가 이미 중단돼 있었다).
이웃 시험 `test_upload_release.py`(완료·정리 직렬화 포함)·`test_ingest.py`·`test_deletion_safety.py`·`test_complete_after_commit_failure.py`·`test_lifecycle.py`(삭제 경로의 409·503)·`test_hot_path_indexes.py`도 통과한다.

## 갱신 (2026-11-20, 통합 검토 UPLOADS-1 — ADR-0084)
결정 2의 '확인과 중단 사이에 이 업로드를 완료하는 요청은 없다'는 같은 묶음의 ADR-0082 뒤로 맞지 않았다. 완료 호출이 시간 초과·연결 오류로 503이 되면
요청 트랜잭션이 되돌려져 행 잠금이 풀리는데, 저장소는 그 완료를 뒤늦게 마칠 수 있다. 그 완료가 확인과 중단 사이에 끝나면 중단은 `NoSuchUpload`(성공으로 본다)나
성공(SeaweedFS 3.80, ADR-0046)이라, 취소·만료 정리는 완성 객체를 남긴 채 세션을 끝냈고 삭제 경로는 그 객체를 뺀 삭제 증명을 냈다(main은 중단 뒤에 확인해 409였다).
이제 처음 확인에서 객체가 없었으면 중단 뒤에 한 번 더 확인하고, 객체가 있으면 결정 2대로(지우거나 삭제 경로는 409), 확인이 실패하면 503이다.
시험 `tests/integration/test_upload_cleanup_late_completion.py`. 확인을 중단 앞에 둔 결정은 그대로다.
