# ADR-0066: 보고서 내보내기 보강 — HWPX 양식은 올릴 때 검사하고, PDF는 아무것도 가져오지 않고 동시 렌더 수를 묶는다

- 상태: accepted
- 날짜: 2026-11-12
- 관련: 10번 요구사항 4.5(PDF·XLSX·HWPX 내보내기)·4.6(보고서 양식 등록), ADR-0018(보고서 렌더러), ADR-0056(제어 문자·속성 따옴표), ADR-0062(요청 DB 차례), ADR-0053(응답 전 확정), 검토 2026-11-12 V7·V8

## 맥락

검토(V7·V8)에서 고치지 못하고 남은 지적이다.

1. **HWPX 양식 검사가 렌더러와 다른 기준이다.** 올릴 때 검사(`check_hwpx`)는 zip을 열어 항목 이름 목록만 봤고, 내보내기(`render_hwpx`)는 모든 항목을 읽고 XML 항목을 UTF-8로 푼다.
   그래서 UTF-16·EUC-KR 양식, CRC가 틀린 항목, 암호화나 모르는 압축 방식의 항목은 `PUT …/hwpx`가 200으로 저장되고, 그 뒤 그 양식의 HWPX 내보내기가 계속 500이었다.
   zip 버전 표시가 새 형식이거나, UTF-8 표시가 있는데 이름이 UTF-8이 아닌 양식은 PUT 자체가 500이었다. ASCII만 쓰고 `encoding="EUC-KR"`을 선언한 양식은 내보내기는 되지만,
   렌더러가 UTF-8로 쓴 한글을 읽는 쪽이 EUC-KR로 읽어 글자가 깨진다.
2. **zip 항목 이름 검사가 POSIX 형태만 막는다.** '/'로 시작하는 이름과 '..' 단계만 거부해 `..\..\evil.xml`, `C:/Windows/evil.xml`, `\\server\share\x.xml` 같은 이름이 통과했다.
   렌더러는 풀지 않고 다시 묶기만 하지만, 내보낸 파일을 받은 사람이 Windows 도구로 풀면 패키지 밖에 쓸 수 있다.
3. **PDF 렌더러가 주소를 가져온다.** WeasyPrint 기본 URL fetcher는 이미지·스타일·글꼴 주소를 http·https·file·data 가리지 않고 가져온다. 지금은 `to_html`이 사람이 쓴 글을 모두
   이스케이프해 그런 자리가 생기지 않지만, 이스케이프 실수 하나로 서버가 내부 주소(SSRF)나 로컬 파일을 읽는다.
4. **PDF 렌더 비용에 상한이 없다.** 렌더는 동기 엔드포인트 안에서 돈다. 계약 한계 길이의 회차 기록 한 건(제목 `t`×200, 시험 항목 `i`×200, 조건 `c `×1000, 결과 `r `×2000)이
   이 기계에서 렌더만 10.6초, 내보내기 요청으로 10.7~16.1초 걸렸다(검토 기계에서는 13.7초). 그동안 요청은 스레드와 DB 차례(ADR-0062, 기본 15)를 쥔다.
   수정 전 같은 보고서의 PDF 내보내기 16건을 동시에 보내면 15건이 92~110초 뒤 200, 1건은 차례를 10초 기다리다 503이었고, 그동안 0.2초 간격으로 보낸 보고서 조회 74건 중 9건이 503이었다.

## 결정

1. **양식 읽기를 한 함수로 모은다.** 올릴 때 검사와 내보내기가 같은 함수(`_template_entries`)로 양식을 읽는다 — 검사를 통과한 양식은 내보낼 때도 같은 길로 열린다.
   - 모든 항목을 실제로 읽는다(압축 해제·CRC 확인). 망가진 zip에서 zipfile과 압축 해제기가 내는 예외(`BadZipFile`, 암호화 `RuntimeError`, 압축 방식·zip 버전 `NotImplementedError`,
     `EOFError`, `OSError`, UTF-8이 아닌 이름·음수 위치 `ValueError`, `zlib.error`, `LZMAError`)는 양식 오류로 바꾼다. 이 목록은 무작위로 망가뜨린 양식으로 정했다
     (무압축·deflate·bzip2·lzma 양식을 2만 번 망가뜨려 검사의 예외 0건, 검사와 렌더의 판정 불일치 0건).
   - 항목은 256KiB 조각으로 읽는다(`_READ_CHUNK`). 이 이미지의 Python 3.12 zipfile은 한 번 읽을 때 푸는 양도 요청한 크기로 묶고(deflate·bzip2·lzma) 헤더에 적힌 크기를 넘는 부분은
     버린다. 그래서 헤더에는 1000바이트라고 적고 실제로는 훨씬 길게 풀리는 압축 자료(압축 폭탄)도 조각 하나 넘게 메모리에 올리지 않는다. 처음 구현은 `ZipFile.read`로 항목을 통째로
     읽었는데, 이것은 압축 해제 한 번에 자료 끝까지 풀고 나서 잘라 내므로 올리기 1MB 남짓에 메모리 2GB를 썼다(검토 지적, 내보내기는 원래 그렇게 읽었다).
   - XML 항목(`.xml`)은 조각마다 엄격한 UTF-8인지 본다(점진 디코더 — 조각 경계에 걸친 글자도 항목 전체를 한 번에 푼 것과 같은 판정). XML 선언에 인코딩이 있으면 UTF-8(`utf-8`·`utf8`,
     대소문자 무관)이어야 한다. 선언은 문서 맨 앞의 짧은 줄이라 앞 4KiB에서만 찾는다. BOM과 선언 없음은 받는다.
   - 올릴 때 검사는 읽은 조각을 바로 버리고 글(str)을 만들지 않는다. 처음 구현은 검사에서도 XML 항목 전체를 글로 풀어, 4바이트 글자 하나가 섞인 큰 항목(올리는 크기 98KB)이면 글자마다
     4바이트가 되어 메모리를 500MB 넘게 썼다(검토 지적). 내보내기만 내용을 모아 글로 푼다.
   - 쓸 수 없으면 `HwpxTemplateError`다. `PUT …/hwpx`는 400 `VALIDATION_ERROR`, 이 검사 전에 저장된 양식으로 내보내면 409 `CONFLICT`("양식을 다시 올리세요")이고
     내보내기 감사(`REPORT_EXPORTED`)를 남기지 않는다. 둘 다 계약에 있던 응답이다. 계약에는 조건을 설명으로 적었다.
2. **항목 이름은 '/'로 나눈 상대 경로만 받는다.** POSIX 형태('/'로 시작·'..' 단계)에 더해 역슬래시(Windows 구분자: `..\`·`C:\`·UNC), `:`(드라이브 문자 `C:x`·NTFS 스트림
   `a.xml:s`), 빈 이름을 거부한다. 글자는 유니코드 범주로 본다: 제어 문자 `Cc`(C0·DEL·C1 — NEL U+0085, CSI U+009B 등), 보이지 않는 서식 문자 `Cf`(방향 제어 U+200E·U+200F·
   U+202A~U+202E·U+2066~U+2069, 폭 없는 문자 U+200B~U+200D, BOM U+FEFF 등), 줄/문단 구분 `Zl`·`Zp`(U+2028·U+2029)가 든 이름을 거부한다. 방향 제어 문자는 `evil‹U+202E›lmx.png`를
   `evilgnp.xml`처럼 보이게 하고, 이름은 오류 안내(400·409의 detail)에도 실린다. 계약이 다른 곳(`ClipRequest.reason`)에서 '제어 문자·보이지 않는 서식 문자'로 정한 글자를 모두 포함한다.
   처음 구현은 C0·DEL만 막아 계약 문장('제어 문자가 든 이름은 거부')과 어긋났다(검토 지적). ZIP 형식의 구분자는 '/'뿐이라 일반 패키지 이름(`mimetype`, `Contents/section0.xml`,
   `META-INF/manifest.xml`, `BinData/그림 1.png`, 디렉터리 항목 `Contents/` 등)은 해당이 없다. 전각 공백(U+3000, `Zs`)·가운뎃점 같은 보이는 글자는 받는다.
3. **PDF는 아무것도 가져오지 않는다.** WeasyPrint `URLFetcher`를 상속해 `fetch`가 언제나 거부하는 fetcher를 넘긴다(http·https·file·data 모두, 막을 때 WARNING 로그 —
   이스케이프가 뚫렸다는 신호다). WeasyPrint 70은 실패 처리에서 fetcher의 속성을 읽어 평범한 함수를 넘기면 거부가 예외(500)가 되므로 상속한다. 글꼴은 API 이미지에 설치한
   `fonts-nanum`을 fontconfig로 찾고(ADR-0018, `backend/Dockerfile`) HTML은 고정 스타일뿐이라, 일반 보고서는 fetcher를 한 번도 부르지 않는다(시험으로 확인).
4. **PDF 동시 렌더 수를 프로세스마다 묶는다.** 새 설정 `REPORT_PDF_MAX_CONCURRENT`(기본 2, `.env.example`·Compose에 넣음). 차례는 기다리지 않는다 — 차례가 없으면 바로
   429 `RATE_LIMITED`와 `Retry-After: 5`(보통 보고서는 1초 안팎, 합성 최악 기록은 10초대). 렌더가 예외로 끝나도 차례를 돌려준다. XLSX·HWPX는 상관없다.
   엔드포인트는 그대로 동기이고 계약에 맞는 요청의 응답은 바뀌지 않는다(429는 계약에 있던 응답).

버린 대안:
- *렌더를 작업 큐(워커)로 옮기기*(검토 방향): 202 + 작업 조회 + 파일 내려받기로 계약과 웹 흐름이 바뀐다. 이번 범위 밖이고 남은 일로 둔다.
- *렌더 시간 상한*: 요청 스레드 안의 WeasyPrint를 밖에서 안전하게 멈출 방법이 없다. 별도 프로세스에서 렌더하면 되지만 프로세스 관리·메모리 상한이 필요해 워커 이전과 함께 본다.
- *기록 수·글자 수로 거부*: 계약 한계 길이의 기록 한 건이 이미 10초대라, 내용으로 막으면 계약에 맞는 보고서를 거부하게 된다.
- *차례를 기다리는 대기열*: 기다리는 요청도 스레드와 DB 차례를 쥐어, 막으려던 일이 그대로 생긴다.
- *렌더 동안 DB 세션을 놓기*: 요청 트랜잭션과 감사 기록의 순서(ADR-0053)를 바꿔야 해 이번에는 하지 않는다.
- *XML 정형성 검사(파서)*: 렌더러는 XML을 해석하지 않고 자리표시자만 바꾸므로 '쓸 수 있는가'와 상관없고, 엔티티 확장 같은 파서 공격면이 새로 생긴다.
- *XML 항목 하나의 크기·압축률 상한(올릴 때 메모리 대책)*: 지금 받는 양식을 새로 거부하게 되고, 헤더에 적힌 크기로는 실제로 풀리는 양을 묶지 못한다. 조각 읽기가 둘 다 없이 묶는다.
- *압축 방식을 무압축·deflate로 한정*: HWPX 양식이 실제로 그 둘만 쓰는지는 확인하지 못했고(확인 필요), 조각 읽기로 bzip2·lzma도 메모리가 묶인다.
- *가져오기를 `data:`만 허용*: 보고서 HTML에 쓸 데가 없다.

## 결과

좋아지는 점: 저장된 양식 때문에 HWPX 내보내기가 500이 되지 않는다(올릴 때 400, 예전 양식은 409로 다시 올리라고 안내). 내보낸 HWPX의 항목 이름이 어느 OS에서 풀어도 패키지 안이다.
PDF 렌더러가 네트워크·파일을 건드리지 않는다. 느린 PDF 렌더가 쥐는 스레드·DB 차례가 프로세스마다 최대 2개라 다른 요청이 503이 되지 않는다.

측정(합성 최악 기록 1건이 든 보고서, 같은 기계·같은 시험 컨테이너, 다른 시험이 함께 돌아 잡음이 있다):

| 항목 | 수정 전 | 수정 후 |
|---|---|---|
| 렌더러만(`render_pdf`) | 10.63초 | 9.77초 |
| 내보내기 요청 1건 | 10.66~16.10초 | 11.52초 |
| PDF 내보내기 동시 16건 | 200 15건(92.5~110.3초), 503 1건(10.05초), 전체 110.3초 | 200 2건(14.1초), 429 14건(0.15~0.22초), 전체 14.2초 |
| 같은 때 보고서 조회(0.2초 간격) | 74건 중 503 9건(각 10.05초), 중앙값 0.08초 | 66건 모두 200, 최대 0.09초 |

렌더 하나의 시간은 줄지 않는다(가져오기를 막는 것과 무관하다). 상한은 피해 범위를 줄일 뿐이다.

양식 읽기 메모리(프로세스를 따로 띄워 최대 RSS 증가를 쟀다. '통째로 읽기'는 수정 전 내보내기와 처음 구현의 검사가 쓰던 `ZipFile.read`):

| 양식 | 올리는 크기 | 검사: 통째로 읽기 → 조각 읽기 | 내보내기: 통째로 읽기 → 조각 읽기 |
|---|---|---|---|
| XML 항목 하나: 'a' 99MiB + 4바이트 글자 하나(deflate, 헤더 크기 정직) | 98KB | +495MB(0.41초) → +0MB(0.06초) | +495MB → +494MB (글로 풀어 바꾸므로 그대로) |
| XML 항목 하나: 헤더는 1000바이트, 실제로는 1GiB로 풀림(deflate) | 1,019KB | +2,046MB(1.53초) → +0MB(0.00초) | +2,046MB → +0MB |

감수할 점:
- 동시에 PDF를 3건 이상 요청하면 429다. 웹 화면은 지금 내보내기 실패를 "내보내기에 실패했습니다"로만 보여 준다(재시도 안내 없음).
- 상한은 프로세스마다다. 전체 상한은 API 프로세스 수 × `REPORT_PDF_MAX_CONCURRENT`다.
- 렌더 하나는 여전히 요청 안에서 10초대까지 걸리고 그동안 DB 차례를 쥔다. 워커 이전·렌더 시간 상한은 남은 일이다.
- 이미 저장된 양식 중 이번 검사에 걸리는 것은 내보내기가 409가 된다(전에는 500이거나 글자가 깨졌다). 다시 올려야 한다.
- 실제 관리기관 양식(T11-f)이 UTF-8이고 일반 항목 이름만 쓰는지는 **확인 필요**다. ':'가 든 항목 이름도 거부한다.
- 올릴 때 모든 항목을 압축 해제하므로(합계 100MiB 한도 안, 위 측정에서 0.1초 남짓) 올리기가 전보다 느리다. 메모리는 조각 몇 개 크기다.
- 내보내기는 XML 항목을 글로 풀어 자리표시자를 바꾸므로 원래대로 양식 크기에 비례해 메모리를 쓴다(위 표, 98KB 양식에 500MB 남짓). 양식은 운영자(`report_template:write`)만 올린다.
  줄이려면 XML 항목 하나의 크기 상한이나 바이트 단위 치환이 필요하다 — 남은 일.
- 메모리 상한은 이미지의 Python zipfile이 한 번에 푸는 양을 묶는 것에 기댄다. bzip2·lzma까지 묶는 것은 시험 컨테이너의 3.12.15에서 확인했다(`python:3.12-slim`은 판을 고정하지
  않는다). 시험이 deflate·bzip2·lzma 압축 폭탄으로 확인하므로 기반 이미지가 바뀌어 동작이 달라지면 시험이 실패한다.
- lzma 항목이 속성에 큰 사전 크기(최대 4GiB)를 적으면 압축 해제기가 그만큼 주소 공간을 잡는다(실제로 쓰는 메모리는 풀린 만큼이다). 가상 메모리 상한(`RLIMIT_AS`)을 둔 환경에서는
  `MemoryError`로 500이 될 수 있다(상한 3GiB에서 확인). Compose 파일에는 그런 상한이 없다.
- 인코딩 선언은 앞 4KiB에서만 찾는다. 선언 안에 공백을 수천 개 넣어 4KiB 뒤에 인코딩을 적은 양식은 그 선언을 보지 않는다(내보낸 글자가 깨질 뿐 500이나 패키지 밖 쓰기는 아니다).

되돌리는 방법: `report_renderers.py`의 `_template_entries`·`_read_entry`·`_entry_chunks`·`_bad_entry_name`을 빼고 `check_hwpx`·`render_hwpx`를 이전 본문으로, `html_to_pdf`의 `url_fetcher`를 빼고,
`export_report`의 `pdf_slots`·`HwpxTemplateError` 처리를 지운다(상한만 끄려면 `REPORT_PDF_MAX_CONCURRENT`를 크게 둔다). 계약의 두 설명을 되돌린다. 마이그레이션 없음.

## 갱신 (2026-11-20, 통합 검토 REPORTS-1 — 항목 종류와 내보낸 항목의 머리글)

맥락: 결정 2는 항목 이름만 봤다. zip 외부 속성의 위 16비트(유닉스 모드)에 심볼릭 링크를 적은 항목(`BinData/up` → `../../../../home`)과
그 링크를 지나는 파일 항목(`BinData/up/.bashrc`)이 든 양식이 `PUT …/hwpx` 200으로 저장됐다. 내보내기는 양식의 `ZipInfo`를 그대로 써서
(`writestr(info, …)`) 링크 항목(모드 0o120777)을 내보낸 파일에 옮겼다. 이름은 패키지 안이지만 링크를 따르는 풀기 도구로 풀면 패키지 밖을 가리킨다.
고치면서 같은 길로 추가 필드도 옮겨진다는 것을 확인했다. 유니코드 경로 추가 필드(0x7075)는 머리글 이름의 CRC가 맞으면 이름을 대신한다.
머리글 이름이 CP437 바이트이고 추가 필드의 CRC를 그 이름의 UTF-8 바이트에 맞춰 두면, 검사는 CRC가 맞지 않아 머리글 이름(패키지 안)을 보고,
내보낼 때 zipfile이 이름을 UTF-8로 다시 쓰면 CRC가 맞아 내보낸 파일의 그 항목 이름이 `../../evil.xml`로 읽혔다(Python zipfile로 읽어 확인).
결과 절의 '내보낸 HWPX의 항목 이름이 어느 OS에서 풀어도 패키지 안이다'가 두 길에서 깨졌다. 양식은 운영자(`report_template:write`)만 올린다.

결정:
1. **항목 종류도 본다.** 올릴 때와 내보낼 때 같은 함수(`_template_entries`)가 외부 속성의 위 16비트에 적힌 파일 종류(`stat.S_IFMT`)를 보고,
   일반 파일·폴더가 아니면(심볼릭 링크·문자/블록 장치·FIFO·소켓) 거부한다 — 올릴 때 400 `VALIDATION_ERROR`(안내에 항목 이름),
   이 검사 전에 저장된 양식은 내보내기 409 `CONFLICT`. 종류를 적지 않은 항목(위 16비트가 0 — Windows 도구가 만든 zip)은 받는다.
   만든 OS 표시(`create_system`)와 상관없이 본다. 풀기 도구마다 어느 OS 표시의 위 16비트를 유닉스 모드로 읽는지 다를 수 있다
   (확인 필요 — 이 기계의 시험 이미지에는 unzip·bsdtar가 없어 도구별 동작은 보지 못했다).
2. **내보낸 항목의 머리글은 새로 만든다(`_export_info`).** 양식 항목에서 이름·시각·압축 방식과 순서만 옮긴다. 외부 속성은 일반 파일 0o644,
   폴더 0o755와 MS-DOS 폴더 표시(0x10)로 쓰고 만든 OS 표시는 유닉스(3)로 둔다. 추가 필드와 항목 주석은 옮기지 않는다. 1이 막지 못한
   메타데이터(위 0x7075처럼 검사와 풀기 도구가 다르게 읽는 값)가 내보낸 파일에 실리지 않는다.

버린 대안:
- *유닉스 표시(`create_system` 3) 항목만 보기*(검토 제안): 다른 OS 표시의 위 16비트를 유닉스 모드로 읽는 도구가 있을 수 있다. 일반 양식의 위 16비트는
  0이거나 일반 파일·폴더라, OS 표시와 상관없이 봐도 새로 거부되는 일반 양식은 없다고 본다(실제 양식은 아래 확인 필요).
- *내보낼 때 링크 항목만 일반 파일로 바꾸고 올릴 때는 받기*: 올린 양식과 내보낸 파일의 항목이 달라지고, 운영자는 양식이 잘못됐다는 것을 모른다.
- *추가 필드만 지우고 양식의 `ZipInfo`는 그대로 쓰기*: 권한·항목 주석처럼 옮길 이유가 없는 값이 계속 남는다. 옮기는 값을 정해 두는 편이 검토하기 쉽다.
- *올릴 때 추가 필드(0x7075 등)를 해석해 거부*: 렌더러는 추가 필드를 쓰지 않으므로 내보낼 때 옮기지 않으면 충분하다.

결과:
- 좋아지는 점: 링크·장치 항목이 든 양식은 올릴 때 400이다. 내보낸 HWPX의 항목은 모두 일반 파일·폴더이고 이름은 검사한 이름 그대로다.
- 감수할 점: 이미 저장된 양식 중 링크 등 항목이 든 것은 내보내기가 409가 된다(다시 올려야 한다). 내보낸 파일의 항목 권한·OS 표시·추가 필드(확장 시각 등)가
  양식과 달라진다 — 한글이 HWPX를 열 때 이 값을 쓰는지와 실제 관리기관 양식(T11-f)의 외부 속성 위 16비트는 **확인 필요**다(이름·순서·압축 방식·시각은 그대로).
- 되돌리는 방법: `_template_entries`의 `_bad_entry_kind` 검사와 `_export_info`를 빼고 `render_hwpx`를 `dst.writestr(info, …)`로 되돌린다. 계약의 두 문장
  (`putReportTemplateHwpx`의 항목 종류, `exportReport`의 HWPX 항목 머리글)을 되돌린다. 마이그레이션 없음.

시험: `tests/unit/test_report_export_hardening.py`에 12개(링크·문자/블록 장치·FIFO·소켓 × 유닉스/MS-DOS 표시 10개는 검사 거부와 렌더 예외, 일반 파일·폴더·종류를
적지 않은 항목은 권한·OS 표시와 상관없이 받음 1개, 내보낸 항목은 이름·시각·압축 방식만 옮기고 외부 속성을 새로 쓰며 추가 필드가 없음 1개),
`tests/integration/test_report_export_hardening.py`에 1개(PUT 400, 저장된 링크 양식으로 내보내기 409·내보내기 감사 없음).
수정 전 코드에서 새 시험 13개 중 12개가 실패하는 것을 확인했다(검사 결과 `[]`, 내보낸 이름 `../../evil.xml`, PUT 200). 나머지 1개(일반 파일·폴더를 계속 받음)는
