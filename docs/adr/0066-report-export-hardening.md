# ADR-0066: 보고서 내보내기 보강 — HWPX 양식은 올릴 때 검사하고, PDF는 아무것도 가져오지 않고 동시 렌더 수를 묶는다

- 상태: accepted
- 날짜: 2026-11-12
- 관련: 10번 요구사항 4.5(PDF·XLSX·HWPX 내보내기)·4.6(보고서 양식 등록), ADR-0018(보고서 렌더러), ADR-0056(제어 문자·속성 따옴표), ADR-0062(요청 DB 차례), ADR-0053(응답 전 확정), 검토 2026-11-12 V7·V8

## 맥락

검토(V7·V8)에서 고치지 못하고 남은 지적이다.

1. **HWPX 양식 검사가 렌더러와 다른 기준이다.** 올릴 때 검사(`check_hwpx`)는 zip을 열어 항목 이름 목록만 봤고, 내보내기(`render_hwpx`)는 모든 항목을 읽고 XML 항목을 UTF-8로 푼다.
   그래서 UTF-16·EUC-KR 양식, CRC가 틀린 항목, 암호화나 모르는 압축 방식의 항목은 `PUT …/hwpx`가 200으로 저장되고, 그 뒤 그 양식의 HWPX 내보내기가 계속 500이었다.
   zip 버전 표시가 새 형식이거나, UTF-8 표시가 있는데 이름이 UTF-8이 아닌 양식은 PUT 자체가 500이었다. ASCII만 쓰고 `encoding="EUC-KR"`을 선언한 양식은 내보내기는 되지만,
   렌더러가 UTF-8로 쓴 한글을 읽는 쪽이 EUC-KR로 읽어 글자가 깨진다.
2. **zip 항목 이름 검사가 POSIX 형태만 막는다.** '/'로 시작하는 이름과 '..' 단계만 거부해 `..\..\evil.xml`, `C:/Windows/evil.xml`, `\\server\share\x.xml` 같은 이름이 통과했다.
   렌더러는 풀지 않고 다시 묶기만 하지만, 내보낸 파일을 받은 사람이 Windows 도구로 풀면 패키지 밖에 쓸 수 있다.
3. **PDF 렌더러가 주소를 가져온다.** WeasyPrint 기본 URL fetcher는 이미지·스타일·글꼴 주소를 http·https·file·data 가리지 않고 가져온다. 지금은 `to_html`이 사람이 쓴 글을 모두
   이스케이프해 그런 자리가 생기지 않지만, 이스케이프 실수 하나로 서버가 내부 주소(SSRF)나 로컬 파일을 읽는다.
4. **PDF 렌더 비용에 상한이 없다.** 렌더는 동기 엔드포인트 안에서 돈다. 계약 한계 길이의 회차 기록 한 건(제목 `t`×200, 시험 항목 `i`×200, 조건 `c `×1000, 결과 `r `×2000)이
   이 기계에서 렌더만 10.6초, 내보내기 요청으로 10.7~16.1초 걸렸다(검토 기계에서는 13.7초). 그동안 요청은 스레드와 DB 차례(ADR-0062, 기본 15)를 쥔다.
   수정 전 같은 보고서의 PDF 내보내기 16건을 동시에 보내면 15건이 92~110초 뒤 200, 1건은 차례를 10초 기다리다 503이었고, 그동안 0.2초 간격으로 보낸 보고서 조회 74건 중 9건이 503이었다.

## 결정

1. **양식 읽기를 한 함수로 모은다.** 올릴 때 검사와 내보내기가 같은 함수(`_template_entries`)로 양식을 읽는다 — 검사를 통과한 양식은 내보낼 때도 같은 길로 열린다.
   - 모든 항목을 실제로 읽는다(압축 해제·CRC 확인). 망가진 zip에서 zipfile과 압축 해제기가 내는 예외(`BadZipFile`, 암호화 `RuntimeError`, 압축 방식·zip 버전 `NotImplementedError`,
     `EOFError`, `OSError`, UTF-8이 아닌 이름·음수 위치 `ValueError`, `zlib.error`, `LZMAError`)는 양식 오류로 바꾼다. 이 목록은 무작위로 망가뜨린 양식으로 정했다
     (무압축·deflate·bzip2·lzma 양식을 2만 번 망가뜨려 검사의 예외 0건, 검사와 렌더의 판정 불일치 0건).
   - XML 항목(`.xml`)은 엄격한 UTF-8로 푼다. XML 선언에 인코딩이 있으면 UTF-8(`utf-8`·`utf8`, 대소문자 무관)이어야 한다. BOM과 선언 없음은 받는다.
   - 쓸 수 없으면 `HwpxTemplateError`다. `PUT …/hwpx`는 400 `VALIDATION_ERROR`, 이 검사 전에 저장된 양식으로 내보내면 409 `CONFLICT`("양식을 다시 올리세요")이고
     내보내기 감사(`REPORT_EXPORTED`)를 남기지 않는다. 둘 다 계약에 있던 응답이다. 계약에는 조건을 설명으로 적었다.
2. **항목 이름은 '/'로 나눈 상대 경로만 받는다.** POSIX 형태('/'로 시작·'..' 단계)에 더해 역슬래시(Windows 구분자: `..\`·`C:\`·UNC), `:`(드라이브 문자 `C:x`·NTFS 스트림
   `a.xml:s`), 제어 문자, 빈 이름을 거부한다. ZIP 형식의 구분자는 '/'뿐이라 일반 패키지 이름(`mimetype`, `Contents/section0.xml`, `META-INF/manifest.xml`, `BinData/그림 1.png`,
   디렉터리 항목 `Contents/` 등)은 해당이 없다.
3. **PDF는 아무것도 가져오지 않는다.** WeasyPrint `URLFetcher`를 상속해 `fetch`가 언제나 거부하는 fetcher를 넘긴다(http·https·file·data 모두, 막을 때 WARNING 로그 —
   이스케이프가 뚫렸다는 신호다). WeasyPrint 70은 실패 처리에서 fetcher의 속성을 읽어 평범한 함수를 넘기면 거부가 예외(500)가 되므로 상속한다. 글꼴은 API 이미지에 설치한
   `fonts-nanum`을 fontconfig로 찾고(ADR-0018, `backend/Dockerfile`) HTML은 고정 스타일뿐이라, 일반 보고서는 fetcher를 한 번도 부르지 않는다(시험으로 확인).
4. **PDF 동시 렌더 수를 프로세스마다 묶는다.** 새 설정 `REPORT_PDF_MAX_CONCURRENT`(기본 2, `.env.example`·Compose에 넣음). 차례는 기다리지 않는다 — 차례가 없으면 바로
   429 `RATE_LIMITED`와 `Retry-After: 5`(보통 보고서는 1초 안팎, 합성 최악 기록은 10초대). 렌더가 예외로 끝나도 차례를 돌려준다. XLSX·HWPX는 상관없다.
   엔드포인트는 그대로 동기이고 계약에 맞는 요청의 응답은 바뀌지 않는다(429는 계약에 있던 응답).

버린 대안:
- *렌더를 작업 큐(워커)로 옮기기*(검토 방향): 202 + 작업 조회 + 파일 내려받기로 계약과 웹 흐름이 바뀐다. 이번 범위 밖이고 남은 일로 둔다.
- *렌더 시간 상한*: 요청 스레드 안의 WeasyPrint를 밖에서 안전하게 멈출 방법이 없다. 별도 프로세스에서 렌더하면 되지만 프로세스 관리·메모리 상한이 필요해 워커 이전과 함께 본다.
- *기록 수·글자 수로 거부*: 계약 한계 길이의 기록 한 건이 이미 10초대라, 내용으로 막으면 계약에 맞는 보고서를 거부하게 된다.
- *차례를 기다리는 대기열*: 기다리는 요청도 스레드와 DB 차례를 쥐어, 막으려던 일이 그대로 생긴다.
- *렌더 동안 DB 세션을 놓기*: 요청 트랜잭션과 감사 기록의 순서(ADR-0053)를 바꿔야 해 이번에는 하지 않는다.
- *XML 정형성 검사(파서)*: 렌더러는 XML을 해석하지 않고 자리표시자만 바꾸므로 '쓸 수 있는가'와 상관없고, 엔티티 확장 같은 파서 공격면이 새로 생긴다.
- *가져오기를 `data:`만 허용*: 보고서 HTML에 쓸 데가 없다.

## 결과

좋아지는 점: 저장된 양식 때문에 HWPX 내보내기가 500이 되지 않는다(올릴 때 400, 예전 양식은 409로 다시 올리라고 안내). 내보낸 HWPX의 항목 이름이 어느 OS에서 풀어도 패키지 안이다.
PDF 렌더러가 네트워크·파일을 건드리지 않는다. 느린 PDF 렌더가 쥐는 스레드·DB 차례가 프로세스마다 최대 2개라 다른 요청이 503이 되지 않는다.

측정(합성 최악 기록 1건이 든 보고서, 같은 기계·같은 시험 컨테이너, 다른 시험이 함께 돌아 잡음이 있다):

| 항목 | 수정 전 | 수정 후 |
|---|---|---|
| 렌더러만(`render_pdf`) | 10.63초 | 9.77초 |
| 내보내기 요청 1건 | 10.66~16.10초 | 11.52초 |
| PDF 내보내기 동시 16건 | 200 15건(92.5~110.3초), 503 1건(10.05초), 전체 110.3초 | 200 2건(14.1초), 429 14건(0.15~0.22초), 전체 14.2초 |
| 같은 때 보고서 조회(0.2초 간격) | 74건 중 503 9건(각 10.05초), 중앙값 0.08초 | 66건 모두 200, 최대 0.09초 |

렌더 하나의 시간은 줄지 않는다(가져오기를 막는 것과 무관하다). 상한은 피해 범위를 줄일 뿐이다.

감수할 점:
- 동시에 PDF를 3건 이상 요청하면 429다. 웹 화면은 지금 내보내기 실패를 "내보내기에 실패했습니다"로만 보여 준다(재시도 안내 없음).
- 상한은 프로세스마다다. 전체 상한은 API 프로세스 수 × `REPORT_PDF_MAX_CONCURRENT`다.
- 렌더 하나는 여전히 요청 안에서 10초대까지 걸리고 그동안 DB 차례를 쥔다. 워커 이전·렌더 시간 상한은 남은 일이다.
- 이미 저장된 양식 중 이번 검사에 걸리는 것은 내보내기가 409가 된다(전에는 500이거나 글자가 깨졌다). 다시 올려야 한다.
- 실제 관리기관 양식(T11-f)이 UTF-8이고 일반 항목 이름만 쓰는지는 **확인 필요**다. ':'가 든 항목 이름도 거부한다.
- 올릴 때 모든 항목을 압축 해제하므로(합계 100MiB 한도 안) 올리기가 전보다 느리다. 내보내기는 원래 그만큼 읽었다.

되돌리는 방법: `report_renderers.py`의 `_template_entries`·`_bad_entry_name`을 빼고 `check_hwpx`·`render_hwpx`를 이전 본문으로, `html_to_pdf`의 `url_fetcher`를 빼고,
`export_report`의 `pdf_slots`·`HwpxTemplateError` 처리를 지운다(상한만 끄려면 `REPORT_PDF_MAX_CONCURRENT`를 크게 둔다). 계약의 두 설명을 되돌린다. 마이그레이션 없음.

시험: `tests/unit/test_report_export_hardening.py` 36개(쓸 수 없는 양식 8종, 무작위로 망가뜨린 양식 400개에서 검사와 렌더의 판정 일치, 패키지 밖 이름 13종, 일반 이름·UTF-8 선언 11가지,
127.0.0.1 미끼 서버와 감사 훅으로 PDF가 http·file을 가져오지 않음 — 같은 HTML을 WeasyPrint 기본값으로 렌더하면 가져오는 것을 대조로 확인, 일반 보고서는 fetcher를 부르지 않음, 렌더 차례),
`tests/integration/test_report_export_hardening.py` 6개(PUT 400 4종, 저장된 양식으로 내보내기 409 뒤 다시 올리면 200, PDF 상한 1에서 두 번째 PDF 429·XLSX 200·끝나면 다시 200).
수정 전 코드에서 30개가 실패하는 것을 확인했다(PUT 200, 내보내기 500, 미끼 서버에 8건 요청, 두 번째 PDF 200 등). 나머지 12개는 정상 양식·인코딩·일반 PDF가 계속 되는지 보는 시험이다.
POSIX 이름 4건은 전에도 검사가 막았고 렌더 예외의 형태만 달랐다. 기존 `test_report_control_chars.py`·`test_report_xlsx_formula.py`·`test_reports_api.py`·`test_t11_reports.py`는 그대로 통과한다.
