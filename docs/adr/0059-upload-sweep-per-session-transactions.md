# ADR-0059: 만료 업로드 정리는 세션마다 짧은 트랜잭션으로 확정한다

- 상태: accepted
- 날짜: 2026-11-12
- 관련: 04번 요구사항 1.5·3.3, ADR-0042(만료 정리 부분 인덱스), 지시서 12번 클립·업로드 검토 C8, tasks.md 23번(세션별 SAVEPOINT)

## 맥락

만료 업로드 정리(`sweep_expired`, 워커가 5분마다)는 만료된 세션 최대 100개를 `FOR UPDATE SKIP LOCKED`로 한꺼번에 잠근 뒤, 한 트랜잭션 안에서 세션마다 SAVEPOINT를 두고
멀티파트를 정리(저장소 호출)하고 예약을 해제했다. 예약 해제(`Quota.settle`)는 기관 쿼터 행을 잠그는데, 그 잠금은 트랜잭션이 끝날 때까지 풀리지 않는다.
그래서 첫 세션을 정리한 뒤부터는 **나머지 세션들의 저장소 호출 내내 그 기관의 쿼터 행을 쥐고 있었고**, 그동안 같은 기관의 새 업로드 예약(`require_room`)이 기다렸다.
검토 재현: 만료 세션 6개·저장소 지연 0.5초에서 새 업로드 생성이 2.5초 늦어졌다. 저장소가 느리거나 만료 세션이 많을수록(최대 100개 × 저장소 지연) 길어진다.

## 결정

1. **후보는 잠그지 않고 고르고, 세션마다 자기 트랜잭션에서 잠그고 정리하고 바로 확정한다.** 후보 조회(`status = 'UPLOADING' AND expires_at <= now ORDER BY expires_at LIMIT 100`)는
   ADR-0042의 부분 인덱스를 그대로 탄다. 세션마다 기본 키로 `FOR UPDATE SKIP LOCKED`를 다시 잡고 상태·만료를 다시 확인한다 — 완료·취소 요청이나 다른 정리기가 잡은 세션은 기다리지 않고 건너뛴다(기존 동작).
2. 세션 하나의 정리 순서는 바뀌지 않는다: 업로드 행 잠금 → 저장소 정리 → 쿼터 행 잠금·예약 해제 → 확정. 쿼터 행 잠금은 저장소 호출이 끝난 뒤에 잡고 바로 확정하므로 DB 작업 동안만 쥔다.
3. 한 세션이 실패하면 그 세션의 트랜잭션만 되돌리고 기록한 뒤 다음 세션으로 간다(SAVEPOINT 때와 같다). 실패한 세션은 다음 주기에 다시 시도한다.

버린 대안: 저장소 정리를 트랜잭션 밖(잠금 전)으로 빼기 — 완료 요청과의 경합(지시서 4번, `test_completion_serializes_with_upload_cleanup`)을 업로드 행 잠금으로 막고 있어 순서를 바꾸지 않는다.
쿼터 정산을 묶음 끝에 한 번만 하기 — 기관별 합계를 따로 들고 다녀야 하고, 중간에 실패하면 이미 확정한 세션과 정산이 어긋난다.

## 결과

좋아지는 점: 정리 중에도 같은 기관의 새 업로드 예약이 저장소 호출을 기다리지 않는다. 정리한 세션은 바로 확정되어, 묶음 중간에 워커가 죽어도 그때까지 정리한 것은 남는다.

감수할 점: 세션마다 트랜잭션을 열어 묶음 하나에 DB 왕복이 조금 늘어난다(세션당 조회 1회 추가). 후보를 고른 뒤 잠그기 전까지 다른 정리기가 같은 후보를 고를 수 있지만, 기본 키 `SKIP LOCKED`와 상태 재확인으로 두 번 정리하지 않는다.
취소·만료 정리가 저장소 오류를 삼키는 문제(검토 C4)는 그대로다 — 미완성 멀티파트 청소 방식은 사람 결정이다(HANDOFF '남은 일' 4절 ④).

되돌리는 방법: `app.services.ingest.sweep_expired`를 한 트랜잭션·SAVEPOINT 방식으로 되돌리고 워커의 `sweep`이 트랜잭션을 열어 넘기게 한다. 마이그레이션·계약 변경 없음.

시험: `tests/integration/test_upload_release.py::test_sweep_does_not_hold_quota_lock_during_storage_calls` — 만료 세션 3개를 정리하면서 저장소 호출마다 다른 연결에서 쿼터 행을 `NOWAIT`로 잠가 본다.
수정 전 코드에서 `[True, False, False]`(두 번째·세 번째 저장소 호출 중 잠겨 있음)로 실패하는 것을 확인했다. `test_hot_path_indexes.py`는 후보 조회가 부분 인덱스를 타는지 본다.
