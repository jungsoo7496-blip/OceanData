# ADR-0075: 운영자 검수 프레임의 '심사 중' 범위와 같은 회차 재검수 표시 규칙

- 상태: accepted
- 날짜: 2026-11-12
- 관련: domain.md 2장(PLATFORM_OPERATOR 바이너리 열), domain.md 5장(share_status), security.md 감사 로그(권한 거부), 14번 요구사항 4.4·6.2·6.3, ADR-0029(긴급 열람), ADR-0053(실패 감사는 따로 확정), 계약 점검 S17·S19·S20·S21

## 맥락

계약 점검(deid 묶음)에서 비식별 검수·태그 작업의 불일치 네 건이 나왔다.

1. **S17** `GET /v1/deid-reviews/{review_id}/frame` — 긴급 열람 승인이 없는 운영자의 원본 프레임 요청은 403인데 감사 행이 없었다.
   권한 표(`require()`)에서 거부된 요청만 `PERMISSION_DENIED`를 남기고, 경로 함수가 직접 내는 403은 남기지 않았다. security.md는 권한 거부를 반드시 기록하라고 한다.
2. **S19** 같은 작업 — 계약은 "운영자는 비식별본(심사 중인 파생본)만", domain.md 2장은 "파생본은 심사 중인 대상만"이라고 하는데, 비식별본 프레임에는 아무 조건이 없었다.
   공유 철회(`WITHDRAW`, 모든 상태 → NONE)나 data_role을 CORE로 바꾼 뒤에도 검수 행이 남아 있어 운영자가 계속 프레임을 받았다.
3. **S20** `POST /v1/deid-reviews/{review_id}/decision` — 미탐(MISSED)은 같은 회차의 다른 PASSED 검수마다 재검수를 새로 만들었다. 원래 PASSED 검수 행은 그대로 PASSED라,
   같은 회차에서 미탐이 또 나오면 재검수가 아직 열려 있는 비식별본에 재검수가 하나 더 생겼다. 재검수 자체를 미탐으로 결정하면 그 비식별본의 옛 PASSED 행이 다시 뽑혀,
   방금 불합격(FAILED)으로 적은 비식별본을 재검수 대기(`review_result=None`)로 되돌리고 또 재검수를 열었다.
4. **S21** `PATCH /v1/assets/{asset_id}/tags` — 사람이 추가한 태그가 이미 모델이 단 자산 전체 태그(같은 `asset_id, tag, t_offset=-1`)면 `ON CONFLICT DO NOTHING`으로 행이 MODEL로 남았다.
   이력에는 사람 ADD가 남는데 응답은 source=MODEL이고, 관측값이 다시 결합되면 날씨 보정(`apply_weather`)이 사람이 확인한 FOG를 지웠다.

S17·S21은 문서에 적힌 동작으로 되돌리는 일이다. S19는 '심사 중'이 어느 상태인지, S20은 무엇을 '재검수 대상으로 표시'하는지 정해야 해서 이 ADR로 남긴다.

## 결정

1. **원본 프레임 거부 감사 (S17).** 승인이 없어 403을 낼 때 `PERMISSION_DENIED`(result=DENIED, 대상 자산, `details={"action": "deid_review:read", "which": "ORIGINAL",
   "reason": "no_break_glass_grant", "review_id": ...}`)를 남긴다. `connection`을 넘기지 않아 요청 트랜잭션과 따로 확정되고, 요청이 실패해도 남는다 (ADR-0053).
   긴급 열람 결정·장비 등록 거부(계약 점검 #15·#25)와 같은 모양이다.
2. **비식별본 프레임의 '심사 중' (S19).** 배정 검수자가 아닌 운영자가 다른 기관의 비식별본 프레임을 요청하면, 그 검수의 원본 `share_status`가
   **PROCESSING·QUALITY_REVIEW·REPROCESS**일 때만 준다. 아니면 403과 `PERMISSION_DENIED`(`which: "DEID"`, `reason: "not_under_review"`)를 남긴다.
   - 공유 심사는 원본 단위로 진행한다(domain.md 4장). 검수가 끝나도(PASSED) 원본이 QUALITY_REVIEW면 운영자가 APPROVED를 판단하는 데 프레임이 필요하므로 그대로 준다.
   - 배정 검수자는 상태와 상관없이 그대로 본다(domain.md 2장 REVIEWER 행은 심사 중 조건이 없다). 메타데이터 조회(목록·상세)는 바꾸지 않는다.
   - 운영자 기관이 가진 자산은 원본 분기와 같이 이 검사를 하지 않는다. 운영자 기관 자산에 승인을 요구할지는 이미 결정 대기 항목이다(HANDOFF 5장).
3. **재검수 표시 규칙 (S20).** 같은 회차에서 PASSED 검수가 있는 비식별본 가운데 다음은 새 재검수를 만들지 않는다.
   - 열린(ASSIGNED) 검수가 이미 있는 비식별본: 이미 표시된 것이다. 새로 만들지 않고 **그 검수 ID를 `recheck_review_ids`에 넣는다**(계약: "재검수로 표시한 검수 ID").
   - 지금 결정한 검수의 비식별본 자신: '다른' 결과가 아니다.
   - `review_result=FAILED`인 비식별본: 이미 공유 대상에서 빠졌고(불합격·다시 만든 결과로 대체), 재검수 대기로 되돌리면 안 된다.
   동시에 같은 회차의 미탐 결정이 둘 오면 둘 다 같은 비식별본에 재검수를 만들 수 있어, 열린 검수를 확인한 뒤 그 비식별본 행을 잠그고(비식별본 ID 순서) 한 번 더 확인한다(통합 검토 뒤로는 그 원본 → 비식별본 순, 원본 ID 순서, ADR-0088).
   결정 중인 다른 검수의 비식별본은 커밋 전까지 ASSIGNED로 보여 첫 확인에서 걸러지므로 잠그지 않는다 — 결정끼리 서로의 행을 기다리지 않는다.
4. **사람 태그 추가 (S21).** 사람 ADD는 자산 전체 태그 행을 upsert해 `source=HUMAN, model_ref=NULL, confidence=NULL`로 바꾼다.
   날씨 보정은 source=MODEL 행만 지우므로 사람이 확인한 태그는 남는다. 영상 프레임별 모델 태그(t_offset ≥ 0)는 다른 행이라 그대로이고, 날씨 보정이 지울 수 있다(기존 의도).

버린 대안:
- S19에서 검수 상태(ASSIGNED)로 '심사 중'을 판단하기 — 공유 철회는 열린 검수를 닫지 않아 철회 뒤에도 보이고, 통과한 뒤 승인 판단에 필요한 프레임은 막힌다.
- S19에서 긴급 열람 승인이 있으면 심사 밖 비식별본도 보이기 — 계약과 domain.md에 파생본의 승인 열람이 적혀 있지 않아 범위를 넓히는 일이다. 승인이 있으면 다운로드 URL로 받을 수 있다.
- S19에서 CANDIDATE·LEGAL_REVIEW도 심사 중으로 보기 — 이 단계에는 이번 심사의 비식별본이 아직 없고, 반려 뒤 재신청한 경우의 옛 비식별본만 있다.
- S20에서 열린 검수가 있으면 응답 목록에서 빼기 — 두 번째 미탐의 응답이 빈 목록이 되어 '표시하지 않았다'로 읽힌다.
- S20에서 재검수를 열 때 원래 PASSED 검수의 상태를 바꾸기(예: SUPERSEDED) — 품질 집계(`quality_report`)가 PASSED·MISSED·REJECTED를 세어 미탐률·재처리 비율이 바뀐다. 결정 기록은 고치지 않는다.
- S21에서 아무것도 지우지 않은 REMOVE를 이력에서 빼기 — 계약과 요구사항 6.2가 정하지 않았고, 사람이 요청한 내용을 남기는 것도 맞는 해석이다. 그대로 둔다.

주인 결정 대기: APPROVED(승인 뒤)를 '심사 중'으로 볼지. 지금은 글자 그대로 읽어 **보지 않는다**. 그래서 승인된 원본의 비식별본에 같은 회차 미탐으로 재검수가 열려도
운영자는 그 프레임을 보지 못한다(배정 검수자는 본다). 운영자가 재검수를 직접 결정해야 하는 운영이면 `UNDER_REVIEW`에 APPROVED를 더하는 것으로 바꾼다.

## 결과

좋아지는 점: 운영자 프레임 거부가 모두 감사에 남는다. 공유를 철회·반려한 원본의 비식별본을 운영자가 더 받지 않는다. 같은 비식별본에 열린 재검수가 하나뿐이고,
불합격한 비식별본이 재검수 대기로 되돌아가지 않는다. 사람이 확인한 태그는 이력과 상태가 같고 날씨 보정이 지우지 않는다.

감수할 점: 승인(APPROVED) 뒤에는 운영자가 비식별본 프레임을 보지 못한다(위 결정 대기). 두 번째 미탐의 `recheck_review_ids`와 감사 `recheck_reviews`에 앞 결정이 만든 검수 ID가
다시 들어간다. 재검수를 만들 때 비식별본 행 잠금이 하나씩 더 생긴다. 사람이 REMOVE한 날씨 태그를 뒤의 보정이 다시 다는 문제와, 다운로드 URL의 운영자 거부 감사는 이번 범위 밖이다.

되돌리는 방법: `app/api/deid.py`의 `UNDER_REVIEW` 분기와 `_frame_denied` 호출, `app/services/deid.py`의 `_open_review`·선택 조건, `app/services/tagging.py` `edit_tags`의
`on_conflict_do_update`를 되돌린다. 마이그레이션·계약 변경 없음.

시험: `tests/integration/test_deid_frame_scope.py`(승인 없는 원본 프레임 403의 감사, 실제 철회 흐름에서 비식별본 프레임 403·감사·검수자 유지, 원본 share_status 8가지별 운영자·검수자 결과),
`tests/integration/test_deid_recheck.py`(두 번째 미탐이 열린 재검수를 다시 쓰기, 재검수 미탐이 자신·불합격 비식별본을 다시 열지 않기,
앞 미탐 결정이 커밋 전일 때 뒤 결정이 비식별본 행 잠금에서 기다렸다가 앞 결정이 연 재검수 ID를 돌려주기),
`tests/integration/test_tag_human_edit.py`(모델 FOG를 사람이 추가한 뒤 맑음 보정에도 HUMAN으로 남기). 수정 전 코드에서 7개 모두 실패하는 것을 확인했다.
동시 결정 시험은 결정 경로가 아니라 서비스 함수(`deid.decide`)를 두 세션에서 직접 부른다. 차례로 결정하면 첫 확인에서 걸러져 잠근 뒤 다시 확인하는 분기를 타지 않기
때문이다. 그 다시 확인을 빼거나 비식별본 행 잠금을 빼면 이 시험이 실패하는 것을 확인했다.
