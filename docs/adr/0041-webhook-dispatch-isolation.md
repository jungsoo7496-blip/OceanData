# ADR-0041: 웹훅 전송 격리 — 전용 스레드, 잠금 없는 가져오기·기록, 한 건 전체 기한, 검사한 주소로 고정

- 상태: accepted
- 날짜: 2026-11-05
- 관련: 04번 요구사항 8.1~8.3, ADR-0030(웹훅 outbox — 이 ADR이 전송·SSRF 부분을 바꾼다), ADR-0014(작업 큐 SKIP LOCKED),
  security.md(테넌트 격리·감사), tech.md HW-3(수치는 설정값)

## 맥락
보안 검토에서 다음을 재현했다.
1. **(중간) 한 기관의 느린 수신 서버가 모든 워커를 멈춘다.** `httpx.post(timeout=5)`는 읽기마다의 기한이라 200 헤더를 바로 보내고
   본문을 몇 초에 한 바이트씩 흘리면 끝나지 않는다(재현 20초, 끝없이 흘리면 무한). 본문도 상한 없이 끝까지 읽었다. 전송은 전송 행을
   `FOR UPDATE`로 잡은 트랜잭션 안에서 했고 구독 행은 SKIP LOCKED 없이 잠가서 다른 워커의 `deliver_due`가 7초 기다렸다. 웹훅 전송이
   작업 처리·임대 회수·정리와 같은 단일 스레드라 그동안 어느 기관의 작업도 돌지 않았다. 기관당 구독 수 상한도 없었다
   (이벤트마다 구독 수만큼 전송 행을 업무 트랜잭션 안에서 만든다).
2. **(낮음) SSRF 검사 빈틈.** 공유 주소 100.64.0.0/10(CGNAT)이 통과했다. httpx가 `HTTPS_PROXY`를 따라가 이 서버의 주소 검사를
   건너뛸 수 있었다. "이름을 풀 수 없음"과 "사설 주소로 풀림"이 다른 문구로 `disabled_reason`에 실려 기관이 내부 이름의 존재를
   알아낼 수 있었다. 검사 때 이름을 한 번 풀고 httpx가 다시 풀어 DNS 재바인딩 여지가 있었다.
3. **(낮음)** 다른 기관 구독 삭제가 404는 주지만 security.md가 요구하는 `CROSS_ORG_ACCESS_ATTEMPT` 감사를 남기지 않았다.

## 결정
1. **전송은 워커 안의 전용 스레드(`webhook-dispatcher`)가 한다.** 작업 루프의 주기 작업 목록에서 뺐다. 보낼 것이 있으면 라운드를
   이어 돌고, 없거나 DB 오류면 `WEBHOOK_DISPATCH_INTERVAL_S` 쉰다. 종료 신호를 받으면 라운드 사이에 멈춘다.
2. **라운드 = 가져오기(짧은 트랜잭션) → 보내기(트랜잭션 밖) → 기록(건마다 짧은 트랜잭션).** 네트워크 I/O 동안 잡는 행 잠금은 없다.
   - 가져오기: 기한이 된 전송이 있는 구독을 가장 오래 기다린 순으로, 기관마다 앞에서 `WEBHOOK_MAX_PER_ORG`(기본 4)개, 모두
     `WEBHOOK_BATCH_SIZE`(기본 20)개 고른다(잠그지 않는 조회). 그 구독 행을 `FOR UPDATE SKIP LOCKED`로 잠근 뒤 새 조회로 다시 확인해
     (후보를 고른 뒤 다른 워커가 먼저 가져갔을 수 있다) 구독마다 가장 오래된 한 건을 `SKIP LOCKED`로 가져와 `SENDING`,
     `attempts+1`, `next_attempt_at = 임대 만료`(기한 × (라운드 건수 + 2))로 커밋한다. 다른 워커도 API도 기다리지 않는다.
   - 보내기: 라운드의 건을 동시에(asyncio) 보낸다. 한 건은 이름 풀기·연결·TLS·요청·응답 헤더까지 전체가 `WEBHOOK_TIMEOUT_S`
     (기본 5초) 안에 끝나야 한다(`asyncio.wait_for`). 상태 코드만 보고 본문은 읽지 않고 연결을 닫는다(헤더는 httpcore 상한 100KiB).
     이름 풀기(`getaddrinfo`)는 취소할 수 없어 데몬 스레드에서 돌리고 기한이 지나면 기다리지 않는다(이벤트 루프 기본 실행기를 쓰면
     `asyncio.run`이 끝날 때 그 스레드를 기다리므로 쓰지 않는다).
   - 기록: 그 건이 아직 내 임대(`SENDING` + 같은 `attempts`)일 때만 쓴다. 구독 행 잠금은 기한보다 오래 기다리지 않는다
     (`lock_timeout`, 그 행은 네트워크에 나가지 않는 짧은 트랜잭션만 잡는다). 재시도·지수 백오프·`WEBHOOK_MAX_ATTEMPTS`번 실패 시
     비활성·남은 전송 취소, 서명 본문·헤더(`X-Signature`·`X-Signature-Timestamp`·`X-Event-Id`)는 ADR-0030 그대로다. 비활성 알림
     메일은 커밋한 뒤 보낸다. 보내는 동안 구독이 지워졌거나 꺼졌으면 실패한 그 건은 재시도하지 않고 취소한다.
   - 워커가 보내다 죽으면 임대가 끝난 `SENDING`을 다른 워커가 다시 보낸다(최소 한 번 — 수신 쪽 중복 제거는 기존 계약의 이벤트 ID).
     `SENDING`은 내부 상태다. API·계약·domain.md 코드표에 없고 컬럼 형식도 그대로라 마이그레이션이 없다.
3. **구독당 한 번에 한 건.** 수신 서버 하나를 동시에 두드리지 않고, 느린 서버는 자기 구독의 처리만 늦춘다.
4. **기관당 구독 상한** `WEBHOOK_MAX_SUBSCRIPTIONS_PER_ORG`(기본 10, 중지된 것 포함·지운 것 제외). 넘으면 409 CONFLICT
   (계약 먼저 고침). 기관별 advisory 트랜잭션 잠금으로 동시에 등록해도 넘지 않는다.
5. **SSRF 보강.**
   - 공인(`is_global`)이 아닌 주소는 모두 막는다. 파이썬이 global로 보는 멀티캐스트 등은 예전 검사를 그대로 둬 막는다.
     IPv4 사상 주소는 안의 IPv4로 판단한다(NAT64 `64:ff9b::/96`은 예약, 6to4는 사설로 이미 막힌다).
   - **주소 고정(재바인딩 차단):** 보내기 직전에 이름을 한 번 풀어 모든 주소를 검사하고, 검사한 주소로만 연결한다. 이름은 `Host`
     헤더와 TLS SNI·인증서 확인에만 쓴다(httpx 문서에 있는 공개 요청 확장 `sni_hostname`). 인증서 확인은 이름 기준 그대로다
     (시험: 고정한 IP로 연결해도 다른 이름의 인증서는 거부). 주소가 여럿이면 연결이 거부될 때만 다음 주소로 간다.
   - `trust_env=False`: `HTTPS_PROXY` 등 프록시 환경변수와 netrc를 따르지 않는다. CA 목록은 전과 같은 httpx 기본이다.
   - 검사와 전송이 같은 URL 해석기(httpx)를 쓰고 포트 범위를 확인한다(해석기 차이로 검사한 이름과 연결 대상이 갈리지 않게).
   - 기관에 보이는 거부 이유는 하나("보낼 수 없는 대상입니다 …"). 못 풀었는지·어느 주소였는지는 서버 로그
     `webhook_target_refused`에만 남긴다. 등록 때 URL 자체(IP 리터럴·내부 이름 등)에 대한 거부 문구는 기관이 쓴 값이라 그대로 둔다.
6. **교차 기관 삭제**는 다른 엔드포인트와 같은 Tenant_Guard(`load_scoped`)로 404 + 감사. 동시 삭제를 막는 행 잠금은 그 뒤
   `refresh(with_for_update)`로 유지한다.

버린 대안:
- 작업 루프에 그대로 두고 라운드 시간 예산만 두기: 동시 전송으로 라운드를 기한 하나로 묶어도, 공격 중에는 작업 루프가 매 주기
  기한만큼 멈춘다(기본 5초/10초 → 작업 처리량 약 1/3 감소). 전용 스레드는 이를 없앤다. 별도 프로세스(compose 서비스)는 배포 단위만
  늘린다(HW-4).
- 동기 httpx를 스레드 풀에서 돌리고 `future.result(timeout)`: 스레드는 취소할 수 없어, 끝없이 흘리는 서버가 풀 스레드를 계속
  붙잡는다.
- 구독당 한 건을 세션 advisory 잠금으로: 보내는 동안 DB 연결을 붙잡는다. 새 열(구독의 임대 시각): 마이그레이션이 필요하고 전송 행의
  상태로 충분하다.
- 사용자 지정 httpcore 네트워크 백엔드로 주소 고정: httpx 내부(`_pool`)를 바꿔야 한다. `sni_hostname`은 공개 API다.
- 비동기 DNS 라이브러리(aiodns·dnspython 등): 새 의존성이고 시스템 resolver(`/etc/hosts`·nsswitch)와 동작이 달라진다.

## 결과
- 좋아지는 점: 수신 서버가 응답하지 않는 동안에도 작업이 처리된다(시험: 1초 안). 느린 수신 서버로 보내는 동안 행 잠금이 없어
  다른 워커가 기다리지 않는다(시험: 0.0초, 검토 재현은 7초). 한 건은 기한에 끊긴다(검토 재현 20초 → 0.1초 — 본문을 읽지 않음,
  헤더를 흘리면 기한에 `TimeoutError`). 한 기관은 한 라운드를 다 차지하지 못한다. 공유 주소·프록시 우회·재바인딩·이름 존재 여부
  노출이 막힌다.
- 감수할 점:
  - 최소 한 번 전송: 보내다 죽거나 기록하지 못한 건은 임대(기본 5초 × 22 = 110초)가 끝난 뒤 다시 보낸다(중복은 `X-Event-Id`로).
  - 구독 하나는 한 번에 한 건이라, 쌓인 건이 많은 구독은 라운드 왕복 시간마다 한 건씩 비워진다(빠른 수신 서버면 초당 수 건).
  - 정상이지만 응답 헤더를 기한 안에 못 주는 수신 서버는 실패로 센다(계약 설명에 적음).
  - 기관별 몫(`WEBHOOK_MAX_PER_ORG`)은 워커마다·라운드마다 적용한다. 워커 W대면 한 기관이 동시에 W × 몫까지 보낼 수 있다
    (구독 수 상한 안에서).
  - 기한이 지난 이름 풀기 스레드는 resolver 자체 시간 제한까지 남는다. 기관별 라운드 몫으로 늘어나는 속도는 묶이지만 개수 상한은
    없다 — 운영 resolver 시간 제한을 짧게 두는 것을 권장(확인 필요).
  - 나가는 프록시가 꼭 필요한 망에서는 웹훅이 나가지 못한다. 그런 배포가 확인되면 별도 설정을 만들고 프록시 쪽에서도 사설 대역을
    막아야 한다(확인 필요).
  - 공인 주소 검사는 이 서버가 보는 DNS·주소 기준이다. 운영망 나가는 방화벽의 사설 대역 차단(ADR-0030의 확인 필요 항목)은 계속
    권장한다. 개발용 `WEBHOOK_ALLOW_PRIVATE_TARGETS=true`에서는 주소를 검사하지 않는다(이름을 못 풀면 `BLOCKED_TARGET`으로 적힌다).
- 되돌리는 방법: `start_webhook_dispatcher` 대신 작업 루프의 주기 목록에 `deliver_due`를 다시 넣으면 된다(라운드 구조와 기한은
  그대로라 멈춤은 기한만큼으로 묶인다). `SENDING` 행은 임대가 끝나면 다시 보내므로 따로 정리할 것이 없다. 계약의 409는 추가라
  그대로 두어도 된다.
